# Changelog — aventyrs-core 0.0.17

Written for projects that consume this library. Everything below is the delta since the range
`0.016.CHANGELOG.md` covers (through commit `24afc73`, "feat, starting with Item, changelog").

`build.gradle` declares `version '0.0.17'`.

Commits in range: `4a91693`, `8c1302f`, `da8b1fb`, plus uncommitted work in the tree. **The
`CombatantSheet` split, the monster package and `AttackDelivery` (§1.1–1.5, §2.5–2.7) are still
uncommitted** and may shift before release. `./gradlew test` passes on the current tree apart
from two pre-existing failures unrelated to this range (see §6).

This version is dominated by one theme: **combat now has two sides.** Defesas became a real
stat, foes became a real type, and both directions of an attack got an entry point. If you only
read one section, read §1.1 — it retypes most of the combat-facing API.

---

## 1. Breaking changes

### 1.1 `CharacterSheet` split into `CombatantSheet` + `CharacterSheet`

The single biggest change in this release. A combat participant is now a
`org.aventyrs.core.sheet.CombatantSheet`, not a `CharacterSheet`. Two implementations exist,
both extending the new `AbstractCombatantSheet` (which holds every shared behaviour once):

| Type | Adds |
| --- | --- |
| `CharacterSheet` | `player`, the experience wallet, Fama |
| `MonsterSheet` (`org.aventyrs.core.monster`) | a foe's four authored stat-block numbers |

Everything else — damage, shields, Mana/Determinação, temporary Ego points, `TemporaryEffect`s,
inventory, the Turn lifecycle, `receiveInteraction` — moved to the shared half and behaves
identically for both.

**Nearly every combat-facing signature retyped.** The rule: anything in the combat, effect,
scene or skill path now takes `CombatantSheet`; only the experience/Fama surface still names
`CharacterSheet`.

```java
// before
public InteractionResult applyTo(CharacterSheet target)
int applyDamage(CharacterSheet sheet, int rawDamage, boolean ignoreDamageReduction)
List<CharacterSheet> getAllies(CharacterSheet sheet)

// after
public InteractionResult applyTo(CombatantSheet target)
int applyDamage(CombatantSheet sheet, int rawDamage, boolean ignoreDamageReduction)
List<CombatantSheet> getAllies(CombatantSheet sheet)
```

Affected across `DamageService`, `DefenseService`, `HitPointsService`, `MagicPointsService`,
`DeterminationPointsService`, `LifeStealService`, `ActiveAbilityService`, `Scene`,
`SceneContext`, `InitiativeEntry`, every `Interaction`/`<Skill>Interaction`, every `Effect`,
`SpellCastingService`, `SkillRollRequest`, `InteractionResult#nextInteraction`,
`SkillCompetencyAbility#resolveDamageBonus`/`#resolveAttackRollBonus`,
`EgoAdvantage#resolveSkillSpecificRollBonus` and `AttributeAbility#resolveDamageReduction`.

**Still `CharacterSheet`, deliberately:** `CharacterAttributeService#upgradeBase`,
`SkillGraduationService#upgradeGraduation`, `FeatService#grantFeat`,
`TitleAbilityService#grantTitleAbility`, `MoralHerdadaAbility#applyStartingFama`,
`RestService#applyRest`.

> **Why those four stayed.** Experience lives on `CharacterSheet`, so a `MonsterSheet` cannot be
> passed to any of them. That is the whole enforcement mechanism for "monsters don't level up" —
> there is no `isMonster()` flag and no runtime guard, because it doesn't compile. See §2.6.

Most consumer code migrates by changing the type name. Code holding a sheet purely to spend XP
or read Fama keeps `CharacterSheet`.

### 1.2 `InitiativeEntry#getCharacterSheet()` renamed to `#getCombatantSheet()`

Field and accessor both, following the retype above.

### 1.3 `Effect` gained an abstract `chainInto`

```java
Effect chainInto(Interaction<CombatantSheet> nextInteraction);
```

A consumer-defined `Effect` implementing the interface directly must now implement this.
**Extend the new `org.aventyrs.core.effect.AbstractEffect` instead** — it provides `chainInto`,
`getNextInteraction()` and a `reportChain(builder)` helper, and every built-in Efeito
(`Sangramento`, `ManaPurge`, `Primor`, `Sabotage`, `RealExecution`, `Definhar`) now extends it.

A subclass's `applyTo` must pass its builder through `reportChain(...)` before building;
forgetting to silently truncates the chain.

### 1.4 `Character.player` is no longer `@NonNull`

A monster has no player. Nothing in main source ever read this field. `Character.builder()` no
longer requires it, and `getPlayer()` may now return `null`. The `player` that still matters is
`CharacterSheet`'s own, which remains required.

### 1.5 `org.aventyrs.core.character.CharacterTemplate` deleted

A 7-line unreferenced stub (`private List<CharacterSkill> skills;`) present since the first
commit. `org.aventyrs.core.monster.MonsterTemplate` now occupies that conceptual space.

### 1.6 `ArmorItem`'s Favor changed the `Item` contract

`Item` was an empty marker interface in 0.0.16. It now declares `getName()`, `getDescription()`,
`getCategory()`, `getWeightClass()`, `getRarity()`, `getPrice()`, `getPhysicalDefenseBonus()`,
`getMagicDefenseBonus()`, `getHardness()`, `getCastingBonus()` and `getFavor()`, plus the
`grantsFavorTo`/`resolveFavorBonus`/`resolveFavorBonuses` defaults. A consumer implementing
`Item` directly must supply the new accessors — or extend `AbstractItem` (`@Builder`).

### 1.7 Enums that grew constants

Extend any exhaustive switch:

- `ModifierType` — `PHYSICAL_DEFENSE`, `MAGIC_DEFENSE` (alongside the pre-existing `DEFESAS`).
- `ItemCategory`/`ItemType` gained real backing types; `ItemRarity` and `ItemWeightClass` are new.

## 2. New features

### 2.1 Defesas (DF/DM) are a real stat — `DefenseService`, `DefenseType`

`ModifierType.DEFESAS` had no reader for several releases. It has one now.

`org.aventyrs.core.character.DefenseType` (`PHYSICAL`/`MAGIC`) carries both halves of its own
mapping — its scoped `ModifierType` and which of an `Item`'s two Defesa columns it reads.

`DefenseService.getTotalDefense(CombatantSheet, DefenseType)` sums, for **both** `DEFESAS` (the
broad type) and the scoped one:

1. the standard three ability sources (attribute abilities, competency abilities *including
   racial*, unlocked excellencies),
2. **equipped items** — the flat DF/DM column plus any Defesa-typed `ItemBonus` in the Favor,
3. the sheet's active `DEFESAS`-typed `TemporaryBonus`es.

The broad/scoped pairing mirrors the existing `SKILL_ROLL_BONUS` + `<SKILL>_ROLL_BONUS` shape,
so a source names whichever it needs and a holder of both still totals correctly.

> **Not clamped at 0**, unlike Reações/RD/RA — a Defesa is a comparison value, not a spendable
> resource, so a net-negative total survives. This is what leaves room for the standard "-2 em
> suas Defesas" penalty.

Two previously-inert grants became real with no change at their granting sites:
`GritoDeGuerraVulcanoInteraction`'s `DEFESAS` Blessing, and `ArmorItem.ROUPA_PESADA`'s Favor.

### 2.2 `EsquivaEApararInteraction` has its own implementation

A new 4-arg overload, mirroring the existing `attackTarget` shape:

```java
applyTo(CombatantSheet target, SceneContext ctx, SkillRoll roll, DefenseType defenseType)
```

It adds the DF/DM pool onto the inherited `skillRollBonus`, **recomputes
`reachedDifficultyLevel`** against the adjusted total (the parent resolves it before this
addition), and applies the **armour-Categoria Destreza penalty**: full Destreza with Leve or
nothing equipped, half with Média, none with Pesada — shifted one bracket lighter by
`ENCOURACADO_E_VELOZ`. Passing `defenseType == null` reproduces the 3-arg behaviour.

### 2.3 Equipment and inventory

- `Character.equipment` (`List<Item>`, mutable) with `equip`/`unequip` — what's worn or wielded.
  Scanned by `DefenseService` and, as a **fourth RD source**, by
  `DamageService#getTotalDamageReduction`, which finally makes `ArmorItem`'s RD Favores real.
- `AbstractCombatantSheet.inventory` with `addToInventory`/`removeFromInventory` — what's
  carried, foes included. Per-sheet acquired state rather than a Character trait.

Both hold **catalog entries, not owned copies**; per-copy state (Dureza remaining, Obra-Prima,
Aprimoramentos) is still unmodeled.

### 2.4 `AttackReceiver` — a foe attacking the player

New package `org.aventyrs.core.combat`. Because the player always rolls, an incoming attack is
resolved as *the defender's Esquiva e Aparar roll* against a GD the attack presents.

```java
IncomingAttackResult r = new AttackReceiver().resolve(IncomingAttack.builder()
        .defender(sheet)
        .difficultyLevel(DifficultyLevel.HARD).attackBonus(2)
        .defenseType(DefenseType.PHYSICAL)
        .defenseRoll(new SkillRoll(List.of(4, 5, 3)))
        .criticalEffect(new Sangramento(CriticalResult.ACERTO_CRITICO_MAIOR))
        .effectChain(new Definhar())
        .build());
```

Reports three **independent** outcomes: `getDefended()`, `getCriticalEffectTriggered()` (the
defence roll was a Falha Crítica) and `getEffectChainTriggered()` (the attack beat the defence by
`EffectChainService`'s margin — 5, or 7 against `RESOLUTO`). An attack can trigger a Corrente
without critting, and vice versa.

**Report-only.** No damage figure is computed — see §3. On a hit it assembles a pre-wired chain
(`Damage → Correntes → Críticos`) onto `getDefenseResult().getNextInteraction()`, which the
caller drains with the existing pipeline loop, supplying `rawDamage` at the head.

### 2.5 `AttackDelivery` — the player attacking a foe *(uncommitted)*

The mirror. Same package, same shapes (`DeliveredAttack`/`DeliveredAttackResult`), same
report-only contract and identical chain assembly.

```java
DeliveredAttackResult r = new AttackDelivery().resolve(
        DeliveredAttack.from(monsterSheet, DefenseType.PHYSICAL)   // fills defenseValue
                .attacker(heroSheet)
                .attackSkill(SkillType.ATAQUE_CORPO_A_CORPO)
                .attackRoll(new SkillRoll(List.of(4, 4, 4)))
                .build());
```

The two entry points are **mirrors, not halves** — neither calls the other, and an exchange runs
one of them per attack. Here the critical trigger is the attacker's *Acerto* Crítico, which is
the direction `CriticalEffect#validateCriticalHit` was always written for.

Throws `IllegalOperationException(NOT_AN_ATTACK_SKILL)` for a non-attack `SkillType`.

### 2.6 Foes — `org.aventyrs.core.monster` *(uncommitted)*

`MonsterSheet` carries the four numbers a foe presents because it never rolls:
`physicalDefense`/`magicDefense` (what a player's Ataque roll must beat) and
`attackDifficulty`/`attackBonus` (what its attacks present to a player's defence roll). They are
**authored on the stat block, not derived** from its Perícias.

Two ways to build one, mirroring `Item`/`AbstractItem`/`ArmorItem`:

```java
// fill in the form — a designed foe
MonsterSheet troll = AbstractMonsterTemplate.builder()
        .name("Troll da Ponte Velha")
        .attributeBase(AttributeDomain.VIGOR, 9)              // past any player ceiling
        .skillGraduation(SkillType.ATAQUE_CORPO_A_CORPO, 12)
        .physicalDefense(19).magicDefense(13)
        .attackDifficulty(DifficultyLevel.HARD).attackBonus(3)
        .lifeMultiplier(7)
        .build().spawn();

// or a generic one, on-scene
MonsterSheet thug = GenericMonster.CAPANGA.spawn();
```

`GenericMonster` ships five archetypes across three threat tiers (`CAPANGA`, `ATIRADOR`,
`BRUTAMONTES`, `CONJURADOR`, `ABERRACAO`). `spawn()` returns a fully independent foe every call —
fresh identity, fresh resource pools and fresh `SkillGraduation` instances (those are mutable, so
sharing them would let one foe's growth raise another's).

Every foe carries the new `org.aventyrs.core.race.Monstruoso` race, deliberately empty:
per-monster traits go on the template's ability lists.

> **Uncapped Attributes and Graduações need no new mechanism.** This core has only ever enforced
> caps on the XP-spending services, never on construction. What the type split prevents is the
> *other* thing — a monster being levelled up. See §1.1.

### 2.7 `Character.lifeMultiplier` and `Character.determinationMultiplier` *(uncommitted)*

Mirroring the `manaMultiplier` field that already existed; `HitPointsServiceImpl` and
`DeterminationPointsServiceImpl` now read the fields instead of their interface constants
(defaults unchanged). This lets a PV budget be tuned apart from Vigor — previously the only way
to make something tanky also inflated every Vigor-governed roll and its Determinação pool.

### 2.8 An `Interaction` can carry its own successor

`Interaction` gained `default Interaction<R> getNextInteraction() { return null; }`, and
`DamageInteraction`/`AbstractEffect` gained `chainInto(...)`. A whole multi-stage chain can now
be assembled up front and handed over as one object; the documented drain loop walks it
unchanged. `DamageInteraction` still forwards only when the hit actually dealt damage.

### 2.9 Items: Favores, and the rest of the catalog

`ItemFavor` (a conditional bonus list gated by `ItemRequirements`), `ItemBonus`
(`ModifierType` + value), `ItemRarity`, `ItemWeightClass`, `AbstractItem`, and the first catalog
enum `ArmorItem` (8 constants, Armadura Completa through Roupa Pesada). `ItemRequirements` checks `getTotal()`, not `getBase()` — whether
a Favor applies is a "can I meet this right now" question.

### 2.10 `Skill.DISADVANTAGE_MALUS`

A flat `-2`, the symmetric counterpart to `ADVANTAGE_BONUS`. `ArmorItem.ARMADURA_COMPLETA`'s
Conjuração column is the first real unconditional Desvantagem.

### 2.11 `CriticalResult#isCriticalFailure()`

The counterpart to `isCriticalSuccess()`. Its first consumer is `AttackReceiver`: on a defence
roll, a critical *failure* is the attacker landing a critical hit.

### 2.12 `CharacterAttributes.of(Map<AttributeDomain, Integer>)`

A static factory building attributes from a domain-to-base map, plus the public `assign(builder,
domain, value)` helper promoted out of `CharacterCreationServiceImpl`. Sets `base` only, and
validates no cap.

## 3. Behavior changes (no signature change)

- **`AtaqueCorpoACorpoInteraction` now resolves target-conditioned bonuses.** The 4-arg
  `applyTo(…, CombatantSheet attackTarget)` overload moved from `AtaqueADistanciaInteraction` up
  to `AbstractSkillInteraction`, gated on `isAttackSkill()`. Consequence:
  `AnoesRacialAbility.ABATEDORES_DE_GIGANTES` now applies to melee, which its rules text always
  covered — a Dwarf swinging at a giant previously got nothing. Calling the overload on a
  non-attack skill is a harmless no-op rather than an error.
- **Neither combat entry point computes damage.** Turning a roll into a raw damage figure needs a
  weapon/dano-roll concept this core doesn't have — the still-manual "Skill → Damage handoff".
  Both resolvers report *which stages fire* and hand back a chain for the caller to feed.
- **Both entry points roll exactly once per attack.** The roll consumes
  `consumeFirstRollThisTurn` and can grant a temporary Ego point, so there is no way to preview an
  attack without spending that state.
- **`CharacterSheet#useExperience` no longer corrupts the balance on a rejected spend.** It
  subtracted before checking; a rejected call now leaves `unUsedExperience` untouched.

## 5. Migration checklist

1. **Retype the combat surface**: `CharacterSheet` → `CombatantSheet` everywhere except the four
   XP-spending services, `applyStartingFama` and `applyRest` (§1.1).
2. Rename `InitiativeEntry#getCharacterSheet()` calls to `#getCombatantSheet()`.
3. Make any consumer-defined `Effect` extend `AbstractEffect`, and route its result builder
   through `reportChain(...)`.
4. Make any consumer-defined `Item` extend `AbstractItem`, or implement its eleven accessors
   (it was an empty marker interface in 0.0.16).
5. Extend exhaustive switches over `ModifierType` (two new constants) and `ItemCategory`.
6. Stop relying on `Character.getPlayer()` being non-null.
7. Delete references to `CharacterTemplate`.
8. Add `NOT_AN_ATTACK_SKILL` to translation bundles.
9. If you build a `Character` outside the Lombok builder (reflection, a DTO mapper, a fixture),
   **set `lifeMultiplier` and `determinationMultiplier`** — `@Builder.Default` won't apply, and
   an omitted field reads 0, collapsing every PV and PD calculation.

## 6. Known issues and deliberate gaps

Carried forward so a consumer doesn't mistake them for bugs:

- **Two pre-existing test failures**, unrelated to this range:
  `SizeCategoryTest#shiftClampsAtThePlusFourCeiling` and
  `CharacterSizeServiceTest#bonusIsClampedAtThePlusFourCeiling` assert a "+4 ceiling" that the
  addition of `SizeCategory.PLUS_FIVE` invalidated. Whether the ceiling or the assertion is wrong
  is an open rules question.
- **The inbound critical trigger has no translation.** `CriticalEffect#validateCriticalHit`
  demands an *Acerto* Crítico, which is right for `AttackDelivery` and wrong for
  `AttackReceiver`, where the trigger is the defender's *Falha* Crítica. A caller there must
  construct the Efeito with a value describing something that didn't happen, and pick the
  Maior/Menor severity by hand instead of inheriting it from the roll.
- **`AttackDelivery` reports but does not apply the attacker's `difficultyReduction`.** It is
  denominated in *níveis*; a foe's Defesa is a flat integer, with no defined conversion. Exposed
  as `getUnappliedDifficultyReduction()`.
- **`AttackReceiver`'s Corrente margin is an inverted reading** of `EffectChainService`'s own
  text, which assumes the triggering roll belongs to the attacker. The constants and RESOLUTO's
  effect are confirmed; applying them to a defender-rolled attack is an inference.
- **A hit fully absorbed by RD/RA drops every Efeito**, since `DamageInteraction` forwards only
  when damage lands. Long-standing behaviour, much easier to hit now.
- **No Reação is spent** when defending — this core tracks counters, not when they may be spent.
- **The armour-Categoria penalty always subtracts Destreza**, even where an attribute
  substitution meant a different Attribute fed the roll.
- **Still missing**: Área de Efeito, damage-type-scoped mitigation, per-copy item state, a PE
  economy, and a Título-side hook into the new Defesas stat (`Santo#getDefesasBonus` computes a
  real number nothing grants yet).
