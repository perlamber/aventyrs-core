# Changelog — aventyrs-core 0.0.21

Written for projects that consume this library. Everything below is the delta since commit
`36763fe` ("type of critical, monster sheet, templates, summons").

`build.gradle` declares `version '0.0.21'`.

This version has one theme: **Ego points are a real currency, in two pools.** They were
previously write-only — granted and spent, but read by nothing, so spending one bought nothing
mechanically. They now have a maximum, an affordability read, a spend that says which pool it drew
from, a per-session recovery, an effect type that can temporarily shrink them, and a first
Vantagem that actually pays out when you spend (`DETERMINACAO_HEROICA`).

**This is a breaking change** — see §1. It is the first release since 0.0.18 to have one.

`./gradlew test` passes on the current tree — 1659 tests — apart from two pre-existing failures
unrelated to this range (see §6.1).

---

## 1. Breaking changes

`CombatantSheet`'s Ego block was reshaped. Three methods changed name or signature, one was
replaced, and `TemporaryPointPool` was deleted.

| 0.0.20 | 0.0.21 | Note |
|---|---|---|
| `int getTemporaryEgoPoints(EgoDomain)` | **same signature**, new meaning | Was a directly-held balance starting at 0. Now "temporary points not yet spent, under the live ceiling" — see §3.1, this is the behavioural break most likely to surprise. |
| `int gainTemporaryEgoPoints(EgoDomain, int)` | `int recoverTemporaryEgoPoints(EgoDomain, int)` | It can no longer accumulate past a ceiling, so "gain" would have been a lie discoverable only at runtime. Returns how many points actually came back. |
| `int gainNonCumulativeTemporaryEgoPoints(EgoDomain, Object, int)` | `int grantTemporaryEgoPointBonus(EgoDomain, Object source, int amount)` | It now raises the *ceiling* rather than the balance. Non-cumulativity per source is unchanged. |
| `int spendTemporaryEgoPoints(EgoDomain, int)` | `EgoPointSpend spendEgoPoints(EgoDomain, EgoPointType, int)` | The pool is now named by the caller, and the return is a report rather than the resulting balance. |
| — | `int getPermanentEgoPoints(EgoDomain)` | new |
| — | `int getMaxTemporaryEgoPoints(EgoDomain)` | new |
| — | `int getAvailableEgoPoints(EgoDomain)` | new |
| `owePendingEgoRecovery` / `applyPendingEgoRecoveries` | unchanged | |

`org.aventyrs.core.sheet.TemporaryPointPool` is **deleted**. It was package-private in effect (only
`AbstractCombatantSheet` used it) and is replaced by `EgoPointPool`, which is package-private for
real. If you referenced it, you were reaching into internals.

Two interfaces grew, with different consequences if you implement them outside this library:

- **`EgoAdvantage`** gained three methods — `resolveExtraSessionEgoRecovery` (§2.3),
  `resolveEgoSpendRecovery` (§2.5) and `resolveEgoSpendBlessings` (§2.7) — but **all three are
  `default`**, so an outside implementation keeps compiling and simply grants none of them.
- **`EgoPointsService`** is entirely new in this release, so none of its six methods can break
  anyone. Worth knowing only if you write your own implementation rather than using
  `EgoPointsServiceImpl`: they are all abstract, none defaulted.

See §5 for the migration, and note step 3 in particular: the replacement for
`spendTemporaryEgoPoints` is not a single method, and choosing the wrong one fails silently.

## 2. New features

### 2.1 Two pools per Ego domain

Every `EgoDomain` on a `CombatantSheet` now holds two spendable pools, both starting full:

```
permanentMax        = character.getEgos().getEgo(domain).getTotal()   // base + variable
permanentRemaining  = max(0, permanentMax - permanentSpent)
temporaryCeiling    = max(0, permanentRemaining + Σ bonus(source) - Σ activeEgoPenalty)
temporaryRemaining  = max(0, temporaryCeiling - temporarySpent)
availableEgoPoints  = permanentRemaining + temporaryRemaining
```

The temporary ceiling tracks permanent points **remaining**, not the permanent maximum — so
**spending a permanent point hurts twice**, removing the point and lowering the ceiling above it:

```java
// Sorte 3, nothing spent: 3 permanent + 3 temporary = 6 spendable.
sheet.spendEgoPoints(SORTE, TEMPORARY, 3);   // 3
sheet.spendEgoPoints(SORTE, PERMANENT, 3);   // 3  → 6 total

// The same character, spending in the other order:
sheet.spendEgoPoints(SORTE, PERMANENT, 3);   // 3, and the ceiling collapses to 0
sheet.spendEgoPoints(SORTE, TEMPORARY, 3);   // 0  → 3 total
```

Nothing special-cases that; it falls out of the arithmetic.

**Permanent points never recover.** Not on Rest, not per session, not anywhere. They are only
*earned*, through `AttributeAbility#resolvePermanentEgoGain`. Nothing reduces them automatically
either — only their holder deliberately spending one.

### 2.2 Spending names its pool, and reports back

```java
EgoPointSpend spend = sheet.spendEgoPoints(EgoDomain.SORTE, EgoPointType.TEMPORARY, 2);
spend.getDomain();   // SORTE
spend.getType();     // TEMPORARY
spend.getValue();    // what ACTUALLY left the pool, after clamping — not what you asked for
```

- **No temporary→permanent fallback** when temporary is short. Falling through would silently
  spend a point that costs twice over.
- **No shorter overload** defaulting the type. The pool is the whole question, not an optional
  input, so the cascading-overload convention doesn't apply.
- **Floors at 0, doesn't throw.** Check affordability yourself with
  `getAvailableEgoPoints(domain) >= n`.

`getType()` is the distinction `AutocontroleAdvantage.DETERMINACAO_HEROICA` needs ("se o ponto for
permanente, o valor recuperado é dobrado") — unresolvable from the sheet after the fact, so it is
reported at the moment of the spend.

### 2.3 `EgoPointsService` — per-session temporary recovery

```java
int SESSION_TEMPORARY_RECOVERY = 1;
int getExtraSessionRecovery(Character character, EgoDomain domain);
void applySessionRecovery(CombatantSheet sheet, EgoDomain chosenDomain);
```

One temporary Ego point per game session — **one in total across all four domains, not one
apiece** — with the recovering player choosing which Ego receives it, hence the parameter. On top
of that, each domain independently receives whatever its held Vantagem grants via the new
`EgoAdvantage#resolveExtraSessionEgoRecovery()` (`MOTIVACAO_DE_MOSES` and `DILETO_DE_TYKHE`, 1
each). Every recovery is bounded by its domain's ceiling.

**Nothing calls it automatically, and nothing should** — a session ends when the people at the
table say it does. The trigger is a GM action in the consuming app, and the bulk overload is what
an end-of-session button maps onto:

```java
// The UI collected each player's chosen Ego; the GM clicks once.
egoPointsService.applySessionRecovery(Map.of(
        anaSheet,   EgoDomain.SORTE,
        brunoSheet, EgoDomain.AUTOCONTROLE));
```

```java
void applySessionRecovery(Map<CombatantSheet, EgoDomain> chosenDomains);
```

**The map is the entire selection.** Only sheets present are recovered — which is exactly how a
consumer excludes a foe on the field or a player who wasn't in the Scene. There is deliberately no
`instanceof CharacterSheet` filter and no "everyone in the Scene" default: which combatants are
the party is the consumer's knowledge, not this core's.

**It is deliberately not idempotent.** A second call recovers again, bounded only by each pool's
ceiling — so a character who had spent two or more temporary points genuinely gains a second one
from a double-click. Preventing that is the consuming app's job: this core has no session boundary
to hang a guard on, and adding one would be the session concept it deliberately lacks. Persist your
own session id plus the set of already-recovered sheet ids, and disable the button once pressed.
`EgoPointsServiceTest` pins the double-application as intended behaviour so it isn't silently
"fixed" later.

### 2.4 `TemporaryEgoPenalty`

```java
sheet.applyEffect(new TemporaryEgoPenalty(EgoDomain.AUTOCONTROLE, 2, 3));  // -2 for 3 Rodadas
```

A dedicated `TemporaryEffect` that lowers a domain's temporary **ceiling**. It rides the ordinary
`applyEffect` / `tickTemporaryEffects` / `finishTurn` lifecycle with no new machinery, expires
normally, and is revocable by reference through `removeEffect`.

**It is never a spend**, and that is why it is its own type. A spend is consumption that would
outlive the penalty's own Duração; a ceiling term reverses the moment the effect expires, giving
back points it had truncated. It never touches permanent points.

**Why not a negative `TemporaryBonus`** with `EgoDomain`-keyed `ModifierType` constants: adding
`AUTOCONTROLE`/`RECURSOS`/`SORTE` would expose them to `ModifierResolver`'s `@Modifier` scan,
implying an ability could `@Modifier`-grant spendable Ego points; and `ModifierType.INITIATIVE`
already exists meaning *turn order*, so one of the four domains would collide semantically with no
way out. If a future clause reduces the **Iniciativa stat**, that is still a
`TemporaryBonus(INITIATIVE, -n, rounds)` — the two are not alternatives.

### 2.5 `DETERMINACAO_HEROICA` — the first Vantagem that reacts to a spend

*"Usar pontos de Autocontrole para qualquer efeito adicionalmente recupera +1d6PV, PM e PD; se o
ponto for permanente, o valor recuperado é dobrado."* Now real:

```java
EgoPointsService ego = new EgoPointsServiceImpl();

// The caller rolled a 4. One roll covers all three pools, per the rules text.
EgoPointSpend spend = ego.useEgoPointsForEffect(
        sheet, EgoDomain.AUTOCONTROLE, EgoPointType.TEMPORARY, 1, 4);
// → 1 temporary Autocontrole point spent; +4 PV, +4 PM, +4 PD recovered.

// The same, from the permanent pool: doubled.
ego.useEgoPointsForEffect(sheet, EgoDomain.AUTOCONTROLE, EgoPointType.PERMANENT, 1, 4);
// → +8 PV, +8 PM, +8 PD.
```

New hook, defaulting to 0, so no other `EgoAdvantage` is affected:

```java
default int resolveEgoSpendRecovery(EgoPointSpend spend, int rolledValue) { return 0; }
```

**A deliberate *use* and an enemy's *drain* are deliberately different call sites.**
`CombatantSheet#spendEgoPoints` also serves `Primor` taking points from a victim against their
will. Had the recovery fired there, a critical hit would partially *heal* the character it just
hit. So `Primor` keeps calling the sheet directly and triggers nothing, while a holder's own
expenditure goes through `useEgoPointsForEffect`. There is no flag on the spend and no observer —
the choice of entry point is the distinction. `EgoPointFeatureTest` pins both directions.

Spending and recovering happen in **one call** rather than leaving the caller to apply the
recovery afterwards, because a separate second call is one a caller can forget.

The hook is consulted only for the Vantagem held in the spend's **own** domain, so an Autocontrole
Vantagem never reacts to a Sorte spend. A spend that took 0 points (an empty pool) earns nothing —
no points were in fact used.

`rolledValue` is the caller's already-rolled die: this core never rolls dice. It is **validated as
a legal d6 face (1–6)**, the same genuine-system-boundary check `SkillRoll` applies to its own
dice — and worth enforcing here specifically, because a negative would otherwise reach
`CombatantSheet#heal` and silently *damage* the character instead of healing them.

`int getSpendRecovery(Character, EgoPointSpend, int rolledValue)` is the pure computation, for a
caller that wants the figure without applying it.

### 2.6 `Scene#getAllParticipants()`

```java
List<CombatantSheet> getAllParticipants();   // active (initiative order), then pending
```

Everyone in the Scene: the union of `getParticipantsInInitiativeOrder()` (the rotation) and
`getPendingParticipants()` (mid-Round joiners). The two halves are **disjoint by construction** —
`addParticipant` routes each entry to exactly one, `startNewRound()` only moves pending→active,
`removeParticipant` searches both — so no de-duplication is needed and no participant can be
missed. A fresh copy, like both halves.

This is what a caller wants when the question is "who is in this Scene" rather than "whose Turn is
it" — building the end-of-session roster above, for instance. The existing two accessors stay;
turn order and not-yet-joined-ness remain real distinctions elsewhere.

### 2.7 `AS_NA_MANGA` — movement off a Ponto de Sorte

*"Imediatamente após utilizar um Ponto de Sorte você pode se mover até 2UD, este movimento não
provoca Reações e ignora terrenos difíceis."* The 2UD is now granted for real, through a second
spend-triggered hook alongside §2.5's:

```java
default List<Blessing> resolveEgoSpendBlessings(EgoPointSpend spend) { return List.of(); }
List<Blessing> getSpendBlessings(Character character, EgoPointSpend spend);   // on EgoPointsService
```

```java
egoPointsService.useEgoPointsForEffect(sheet, EgoDomain.SORTE, EgoPointType.TEMPORARY, 1, 4);
sheet.getTemporaryBonus(ModifierType.MOVEMENT);   // → 2
```

Either pool counts — "utilizar um Ponto de Sorte" doesn't distinguish permanent from temporary, so
unlike `DETERMINACAO_HEROICA` this ignores `EgoPointSpend#getType()`. The grant is a
`Blessing(MOVEMENT, 2, …)`, the identical shape `InitiativeAdvantage.POSICIONAMENTO_ESTRATEGICO`
already used for its own +2UD, off a different trigger. It lands on the sheet as a
`TemporaryBonus`, so it flows into movement exactly where `MovementService`'s javadoc says a
caller adds `getTemporaryBonus(ModifierType.MOVEMENT)` on top of the permanent total.

Unlike initiative blessings, these are granted **straight to the spender** rather than returned for
a caller to route — who spent the points is unambiguous, the same reasoning that lets
`AbstractSkillInteraction` apply `DESTINO_FAVORAVEL`'s Ego point on the spot. A `TargetScope` other
than `SELF` therefore has no meaning on this hook yet.

**Both qualifiers are no-ops in this core, not omissions.** "Não provoca Reações" would exempt the
movement from a movement-triggers-Reação mechanism that doesn't exist, and "ignora terrenos
difíceis" from a per-movement difficult-terrain cost that doesn't exist either (`TerrainType`
describes a whole Scene, not a square). Being exempt from nothing costs nothing, so a plain +2UD is
presently an exact model — but both constants need revisiting the day either system lands.

**One approximation worth knowing:** the grant lasts 1 Rodada, the shortest a `TemporaryBonus` can
express, where the text says "imediatamente". This core has no one-shot movement allowance and
never executes movement at all — `MovementService` computes a total, it doesn't spend it — so the
2UD is added to the Rodada's allowance rather than to a discrete immediate step.

## 3. Behavior changes (no signature change)

### 3.1 Every sheet now starts with Ego points instead of zero

This is the change most likely to affect your tests. `getTemporaryEgoPoints(domain)` used to
return 0 on a fresh sheet; it now returns that domain's ceiling. A Character whose Egos are all at
the default (base 2, variable 0) starts with **2 permanent and 2 temporary points per domain**,
and `getAvailableEgoPoints` reports 4.

A consequence worth checking in your own suites: **a recovery against a full pool is a no-op**, so
any assertion of the form "owe a recovery, rest, expect N points" now passes for the wrong reason
unless something was spent first. Three tests in this repo had exactly that shape.

### 3.2 `Primor` no longer over-promises its refund

`Primor` registered its `PendingEgoRecovery` for the amount it *tried* to spend. Against a target
holding fewer temporary points than it drains, the Rest handed back points the victim had spent
itself. It now registers `spend.getValue()` — what actually left the pool — and reports the same
figure on `InteractionResult#egoLossValue`.

A target with 1 temporary Sorte point hit by Primor Maior loses 1, not 2, and gets 1 back.

### 3.3 `DESTINO_FAVORAVEL` raises a ceiling rather than handing over a point

`CharismaAbility.DESTINO_FAVORAVEL`'s "um ponto temporário, não cumulativo" on a Sucesso Crítico
Maior now widens the temporary ceiling in Sorte and Autocontrole, still non-cumulatively per
source. `InteractionResult#egoGainDomains` reports the same domains as before.

### 3.4 Rest still does not refill the temporary pool

Stated explicitly on `RestService#applyRest` now, because it looks like an omission. Temporary Ego
recovery is scoped to a *session*, not a Descanso; the only Ego points a Rest returns are ones an
effect specifically promised back. `RestServiceImpl` is unchanged.

## 4. New `TranslatableMessages` keys

`INVALID_DIE_ROLL` — thrown by `EgoPointsService#getSpendRecovery` (and therefore
`#useEgoPointsForEffect`) when `rolledValue` isn't a legal d6 face. `spendEgoPoints` itself still
floors rather than throwing, so it needs no message.

## 5. Migration checklist

1. `gainTemporaryEgoPoints(d, n)` → `recoverTemporaryEgoPoints(d, n)`. **Check the semantics**:
   this now restores previously-spent points and cannot exceed the ceiling. If you were using it
   to *add* points a character didn't have, you want `grantTemporaryEgoPointBonus` instead.
2. `gainNonCumulativeTemporaryEgoPoints(d, src, n)` → `grantTemporaryEgoPointBonus(d, src, n)`.
   Same arguments, same non-cumulative-per-source behaviour; it raises the ceiling now, and the
   return is the resulting temporary remaining.
3. `spendTemporaryEgoPoints(d, n)` → **one of two things, and the choice matters** (§2.5):
   - The character is **deliberately using** points for some effect →
     `EgoPointsService#useEgoPointsForEffect(sheet, d, EgoPointType.TEMPORARY, n, rolledValue)`.
   - Something is **draining** points from them against their will →
     `sheet.spendEgoPoints(d, EgoPointType.TEMPORARY, n)`.

   Both return an `EgoPointSpend` rather than the resulting balance — call `getValue()` for what
   was actually spent, or re-read `getTemporaryEgoPoints(d)` if you wanted the balance. **Picking
   the bare sheet call for a deliberate use is a silent bug**: it compiles, it spends correctly,
   and a character with `DETERMINACAO_HEROICA` simply never receives the recovery they are owed.
   If you are unsure which you have, ask whether the character chose to spend.
4. If you route a deliberate use through `useEgoPointsForEffect`, **you must supply the 1d6
   yourself** — this core never rolls dice. One roll covers all three pools. It is validated as a
   legal d6 face (1–6) and throws `IllegalOperationException`/`INVALID_DIE_ROLL` otherwise, so
   don't pass a pre-doubled value or a placeholder `0`.
5. Re-check any test or UI that assumed Ego points start at 0 (§3.1).
6. If you display Ego points, `getMaxTemporaryEgoPoints` and `getPermanentEgoPoints` are what let
   you render "2/3" rather than a bare count.
7. If you persist sheet state, note that **neither pool is exposed as a raw spent-counter**. What
   round-trips today is what the readers report; a DTO that needs to restore a partially-spent pool
   has no setter to restore it through. See §6.3.

## 6. Known issues and deliberate gaps

### 6.1 Carried forward from 0.0.18

The same two pre-existing test failures, unrelated to this range and still unaddressed:
`SizeCategoryTest#shiftClampsAtThePlusFourCeiling` and
`CharacterSizeServiceTest#bonusIsClampedAtThePlusFourCeiling`. Both concern `SizeCategory#shift`
clamping to the full 15-value array while its javadoc claims a -4/+4 range.

### 6.2 Only Ego spends have a reaction path

`EgoPointsService#useEgoPointsForEffect` resolves a held `EgoAdvantage` against a completed Ego
spend, which is what makes `DETERMINACAO_HEROICA` work. **PV/PM/PD spends have no equivalent** —
`spendMagicPoints`/`spendDeterminationPoints`/`applyDamage` return no report and nothing reacts to
them, so a trait keying off those still can't be expressed. An observer/event mechanism remains
deliberately rejected; the pattern to follow is a service entry point that does the thing and
resolves the reaction together.

`SorteAdvantage.AS_NA_MANGA` is now real — see §2.7.

### 6.3 A partially-spent pool cannot be reconstructed from outside

`EgoPointPool` is package-private and neither pool's `spent` counter has a setter. A sheet rebuilt
from persisted state comes back with both pools full. This matches how `ResourcePool` already
behaves for PV/PM/PD (`applyDamage`/`spendMagicPoints` are the only ways in), so it is consistent
rather than novel — but it is worth knowing if you persist Ego state.

### 6.4 The clamp is lossy in one direction

When a ceiling falls below what has been spent, `temporarySpent` is normalized down to it — so a
fallen ceiling can't leave a hidden debt that swallows the next recovery. The one lossy case:
spend truncated while a penalty was active is not restored if a permanent point is later *earned*
while still over-spent. Tracking pre-clamp overspend to fix that would buy correctness only in a
scenario requiring a permanent Ego point to be earned mid-session, in a domain simultaneously
over-spent and penalized. Flagged in `EgoPointPool`'s javadoc.

### 6.5 A permanent point earned after a sheet exists is invisible to it

`AbstractCombatantSheet.character` is `final`, while `AttributeAbilityServiceImpl#grantAttributeAbility`
applies a permanent Ego gain by returning a *rebuilt* `Character`. So the sheet keeps reading the
old maximum until a new sheet is built from the new Character. Pre-existing — the same ordering gap
`MoralHerdadaAbility#applyStartingFama` sits on — and not introduced here.

### 6.6 Two clauses remain blocked, on narrower gaps than before

- **`MOTIVACAO_DE_MOSES` / `DILETO_DE_TYKHE`** — their amounts are real data now. Only the trigger
  is missing: no game-session boundary calls `applySessionRecovery`.
- **`GnoseAbility.ESTABILIDADE_EMOCIONAL`** — its trigger is now *expressible*
  (`getAvailableEgoPoints(AUTOCONTROLE) == 0`) and its grant is `recoverTemporaryEgoPoints`. Still
  blocked on game-session tracking and on a "next Rodada" delayed-grant mechanism, which nothing
  in this core has.

### 6.7 Nothing drives the Scene loop

Unchanged from 0.0.18 and 0.0.20, and newly relevant: `Scene#next()` — and therefore `finishTurn()`
and `tickTemporaryEffects()` — has no production caller in either downstream consumer. A
`TemporaryEgoPenalty` will never expire on its own unless something ticks the loop.
