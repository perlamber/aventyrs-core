# Changelog — aventyrs-core 0.0.44

**A held Título can acquire an Especialização after awakening.** Until now it could not: the
Especializações were whatever the constructor was handed, and `AventyrTitle` exposed only
`grantAbility`. That left a real dead end — every `SantoAbility` names "Requer 1 Especialização",
and `DespertarAntecipadoFeat` awakens a Santo holding none, so such a character could never acquire
anything at all, forever.

## ⚠️ Breaking changes

- **`AventyrTitle` gains `grantSpecialization(AventyrTitleSpecialization)`.** Any implementation
  outside this repo must supply it. Abstract rather than defaulted, for the reason
  `getArchetype()` already is: every Título holds Especializações, so there is no sensible
  fallback, and a silent no-op default would make an acquisition look like it worked.

## Why it is a second mutator, not one

An `AventyrTitleSpecialization` **is** an `AventyrTitleAbility` — it extends that interface. So a
single `grantAbility` would have compiled and quietly done the wrong thing: the Especialização
lands in the Habilidade list, where `getSpecializations()` never reports it. That is not merely
untidy. `AventyrTitleAbility#getRequiredSpecializations` counts exactly what `getSpecializations()`
returns, so a misfiled Especialização leaves every "Requer 1 Especialização" Habilidade
unacquirable — the acquisition appears to succeed and nothing downstream changes.

`TitleAbilityServiceImpl#grantTitleAbility` routes each kind to its own mutator, so both arrive
through the one validated entry point callers already use, with its "is this Título held" and
`isEligible` gates intact.

## Santo

- `specializations` is now a defensive mutable copy, matching what `abilities` already did — the
  same reason: `List.of(...)` is the common case at a call site, and it rejects an append.
- `grantSpecialization` refuses a constant from another Título's catalog rather than storing it.
  This is the enforced half of each constant's own "Apenas 'Santos' podem adquirir esta
  especialização" line, and it is load-bearing beyond taste: a foreign constant would be counted by
  `getSpecializationAndSupremaCount()`, inflating Despertar's own Defesas and Duração arithmetic.

## Not changed

- **No cost, no timing rule.** An Especialização costs nothing and requires nothing, exactly as a
  plain Habilidade already did — neither has a cost documented anywhere in the rules text, and
  inventing one here would be this core making up a rule. The Suprema allotment is untouched: an
  Especialização is not a Suprema and never spends a slot.
- "Apenas 'Santos' podem adquirir esta especialização" remains unenforced *as an eligibility check
  on the character* (only on the catalog), per this codebase's standing "no eligibility validation
  service" restraint.
