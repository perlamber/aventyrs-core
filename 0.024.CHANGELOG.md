# Changelog — aventyrs-core 0.0.24

Written for projects that consume this library. This document covers **two themes**:

- **Part I (§1–§7)** — recording the choice a player makes when acquiring a Talento whose rules
  text opens with *"escolha uma Perícia / um tipo de terreno / um tipo de arma"*.
- **Part II (§8–§11)** — **the Skill Roll protocol**: a roll can now state the Grau de
  Dificuldade it was made against, and the result reports whether it beat it. **This is the part
  a client and an API layer need to act on.**

Other work in the `0.0.24` range, if any, is not described here.

`./gradlew test` passes on the current tree (`build -x javadoc` is green). ~30 tests are new
for this theme, across 7 new test classes plus additions to
`GeneralFeatEffectIntegrationTest`.

**There is one non-breaking behaviour change** (§3) and **two `default`-only interface
additions** (§1). An outside implementation of `Feat` keeps compiling untouched.

---

## 1. Breaking changes

**None.** Every addition to `Feat` is a `default` method:

| Interface | Added | Consequence for an outside implementor |
|---|---|---|
| `Feat` | `default Feat catalogEntry()` → returns `this` | none |
| `Feat` | `default int resolveSkillRollBonus(SkillType, SceneContext, SkillTrait, Character, AttackSource)` → delegates to the 4-arg form | none |
| `Feat` | `default int resolveCriticalMarginIncrease(SkillType, SceneContext, Character, AttackSource)` → delegates to the 3-arg form | none |

The two new `resolve*` overloads follow the same **defaulting** (not cascading) relationship
`SkillCompetencyAbility#resolveSubstituteAttributeDomain(AttackSource)` already uses: the
longer form falls through to the shorter one, so a `Feat` that overrides only the shorter form
keeps working. Override the **longer** form for a clause scoped to *what the attack was made
with*; override the shorter one otherwise.

---

## 2. New features

### 2.1 The problem

A `Feat` is an enum constant — one singleton shared by every character. `PeritoFeat.FOCO_EM_PERICIA`
("escolha uma perícia, adquira vantagem nas rolagens da Perícia escolhida") cannot hold *which*
Perícia a given character picked: two players choosing differently would need the same constant to
answer two ways. Roughly sixteen constants across the catalog were blocked on this, and
`PeritoFeat`/`FeericoFeat`'s own javadocs flagged it as a decision to make once.

### 2.2 The shape — a choice-carrying `AbstractFeat` subclass

The enum constant **stays** as the catalog / rules-text entry. A hand-written
`final class <Name>Feat extends AbstractFeat` is the *acquired, per-character* form, carrying the
pick as a `@NonNull` constructor field — exactly the split
`org.aventyrs.core.skill.artes.ArtesAprimorarComArteAbility` keeps against
`ArtesCompetencyAbility.APRIMORAR_COM_ARTE`.

```java
// the player picked Atletismo when acquiring Foco em Perícia:
featService.grantFeat(character, sheet, FocoEmPericiaFeat.of(SkillType.ATLETISMO));
```

`AbstractFeat` was already the sanctioned `non-sealed` extension point with a public
constructor; this is a first-party use of it. The subclass:

- delegates `getFeatCategory()` / `getDescription()` / `getFeatRequirements()` to the enum
  constant via `super(...)`;
- overrides `catalogEntry()` to return the enum constant (see §2.3);
- overrides whichever `resolve*` hook(s) its clause reaches, branching on the choice;
- exposes a `static Optional<C> chosenBy(Character)` so **dependent** Talentos in the same tree
  — which stay plain enum constants — can read the pick (mirrors
  `PeritoTeoricoAbility.resolveAttributeDomain`).

**Not a stateful `Feat` interface.** Making `Feat` itself stateful would mean abandoning enums
for the whole catalog — 34 tree enums, `FeatCatalog`'s `getPermittedSubclasses()` reflection,
every `requiredFeat` identity check — to serve sixteen constants. The `Feat` `resolve*` hooks
are already parameterized with `SkillType` / `SceneContext` / `AttackSource`, so the choice
field feeds them directly, with **no service changes** — every service already gives
`character.getFeats()` an explicit `.map(feat -> feat.resolve*(...))` pass.

### 2.3 `Feat#catalogEntry()` — keeping identity working

`Feat` identity is compared in two places that a hand-written instance would otherwise fail:

- `Feat#isEligible` — the `requiredFeat` prerequisite check;
- `FeatCatalog#availableFor` — the "not already held" filter.

Both now compare against `held.catalogEntry()` instead of object identity, so a
`FocoEmPericiaFeat` in `Character#feats` still counts as `PeritoFeat.FOCO_EM_PERICIA` — a
dependent Talento requiring it becomes eligible, and the base Talento drops off the "available"
list. A choice instance is deliberately **not** given a custom `equals`; the one-directional
accessor is the whole bridge.

The choice instance is never listed by `FeatCatalog` (it is not an enum). The consumer lists
the catalog (bare enum constants), the player picks, the consumer constructs the instance and
passes it to the **existing** `FeatService#grantFeat(Character, CharacterSheet, Feat)`.

### 2.4 `AttackMethod` — the weapon-type choice

New enum `org.aventyrs.core.item.AttackMethod`: the weapon `ItemCategory` constants
(`BOW`, `THROWABLE`, `CROSSBOW`, `WHIP`, `CLUB`, `LIGHT_BLADE`, `HEAVY_BLADE`, `SPEAR`,
`PROJECTILE`) plus `NATURAL_WEAPON` and `OFFENSIVE_MAGIC` — the granularity the rules mean by
"um tipo de arma, armas naturais ou magias ofensivas". `matches(AttackSource, Character)`
classifies a delivered attack:

- weapon constants → `source instanceof Weapon w && w.getCategory() == category`;
- `NATURAL_WEAPON` → via `Character#treatsAsNaturalWeapon`, so a Talento that reclassifies a
  weapon as natural is seen here too;
- `OFFENSIVE_MAGIC` → `source instanceof Spell`;
- `null` source → always `false`.

Reached through the new trailing-`AttackSource` overloads of `resolveSkillRollBonus` /
`resolveCriticalMarginIncrease` (§1), threaded in by `AbstractSkillInteraction` from the 5-arg
`applyTo`.

### 2.5 The six wired constants

| Talento | Class | Choice | Effect wired |
|---|---|---|---|
| `PeritoFeat.FOCO_EM_PERICIA` | `FocoEmPericiaFeat` | `SkillType` | Vantagem on the chosen Perícia |
| `SobrevivenciaFeat.TERRENO_PREDILETO` | `TerrenoPrediletoFeat` | `TerrainType` | +2 DF & DM and Vantagem (Furtividade, Conhecimentos: Natureza) while in the chosen terrain |
| `FeericoFeat.ADOTADO_POR_SYLPH` | `AdotadoPorSylphFeat` | `Set<SkillType>` | Vantagem on each chosen Perícia |
| `DuelistaFeat.ESPECIALISTA_EM_ARMA` | `EspecialistaEmArmaFeat` | `AttackMethod` | Vantagem on an attack roll delivered with the chosen method |
| `ArtilhariaFeat.ATIRADOR_PERFEITO` | `AtiradorPerfeitoFeat` | `AttackMethod` | Vantagem vs a target at Distância Média or beyond, with the chosen method |
| `AssassinoFeat.ACERTO_CRITICO_APRIMORADO` | `AcertoCriticoAprimoradoFeat` | `AttackMethod` | +1 Margem Crítica on an attack delivered with the chosen method |

Dependent constants that read a sibling's pick via `chosenBy` and gained a wired half:
`SobrevivenciaFeat.MESTRE_DE_CACA` (Margem Crítica +1 and Perícias de Ataque Vantagem while in
the Terreno Predileto), `DuelistaFeat.MAESTRIA_EM_ARMA` (Margem Crítica +1 with the
`ESPECIALISTA_EM_ARMA` method). `AssassinoFeat.ARCANISMO_AVASSALADOR` — "Magias ofensivas …
+1 + Títulos Arcanos Despertos" — is now real through the same `AttackSource` hook (no player
choice of its own; scoped to `OFFENSIVE_MAGIC`).

### 2.6 Stale-comment fixes made along the way

- **`AssassinoFeat` class javadoc** claimed `resolveCriticalMarginIncrease` "does not exist on
  `Feat`". It has existed since the `Feat` roll-hook work; the javadoc now describes the real
  remaining limitation: the margin widens the Margem Crítica **Menor only** —
  `SkillRoll#getCriticalResult(int)` applies it to that tier, while Acerto Crítico Maior is a
  literal triple-6, margin-independent. A clause that also names the Maior tier gets its Menor
  half and nothing more; a Maior widening would need its own explicit mechanism.
- **`SobrevivenciaFeat.TERRENO_PREDILETO`** cited "TerrainType's constants are not the six
  named here". They are: `URBAN`=Cidades, `CAVE`=Subterrâneo, `MOUNTAIN`=Montanhas,
  `FOREST`=Florestas, `DESERT`=Desertos, `AQUATIC`=Aquáticos.
- ~15 dependent-constant TODOs re-narrowed from "no choice representation" to their actual
  remaining blocker (a per-Rodada attack counter, a drawn-weapon state, an Atributo-grant hook,
  the acquisition-slot gap, …).

## 3. Behavior changes (no signature change)

**`AbstractSkillInteraction` now threads the delivered `AttackSource` into the `Feat`
roll-bonus and critical-margin scans.** Before, `sumFeatRollBonuses` /
`sumCriticalMarginIncrease` received no `AttackSource`; now they receive the 5-arg `applyTo`
parameter and pass it to the new `Feat` overloads.

Consequence for a consumer using only shipped Talentos: **none until a character holds one of
the §2.5 constants.** A held `EspecialistaEmArmaFeat` / `AtiradorPerfeitoFeat` /
`AcertoCriticoAprimoradoFeat` (or `ARCANISMO_AVASSALADOR`) now contributes to a roll made via
`applyTo(target, sceneContext, skillRoll, attackTarget, attackSource)` when `attackSource`
matches its chosen `AttackMethod`. A caller that never passes an `attackSource` sees no change —
`AttackMethod.matches(null, …)` is `false`.

## 4. New `TranslatableMessages` keys

**None.** Grant validation reuses the existing `FEAT_PREREQUISITE_NOT_MET`.

## 5. Migration checklist

Short, because nothing was removed or renamed.

1. **Nothing to change** if you consume the shipped Talentos and services. Recompile and go.
2. **To offer an acquisition-time-choice Talento in a UI:** list the catalog as before
   (`FeatService#getAvailableFeats` returns the bare enum constants), let the player pick, then
   construct the matching class (`FocoEmPericiaFeat.of(...)`, `EspecialistaEmArmaFeat.of(...)`,
   …) and pass **that** to `FeatService#grantFeat`. No new service method.
3. **If you resolve attacks and want the new method-scoped bonuses:** call the 5-arg
   `applyTo(target, sceneContext, skillRoll, attackTarget, attackSource)` with the `Weapon` /
   `Spell` as `attackSource`. Shorter overloads still work and simply grant nothing
   method-scoped.
4. **If you author your own `Feat`** (extending `AbstractFeat`): you may override
   `catalogEntry()` (only needed for a choice-carrying class) and the new 5-arg `resolve*`
   overloads. You do not have to.
5. **`FeatCatalog` size assertions:** unchanged — the choice classes are not enums and are not
   listed. Only the enum constants are.

## 6. Known issues and deliberate gaps

### 6.1 Choices this release does **not** model

| Clause shape | Blocker |
|---|---|
| "escolha um Atributo, recebe Bônus Racial / uma Habilidade" (`DestinoFeat.PRODIGIO`/`GENIALIDADE`, `HumanoFeat.LIMIAR_DA_EVOLUCAO`, `MonstruosoFeat.DUAS_CABECAS`) | a Talento cannot grant an Atributo bonus or a free ability slot — the choice *could* be recorded, but there is no hook to spend it on |
| "escolha um Ego, adquire uma Vantagem" (`DestinoFeat.AUTOCONHECIMENTO`) | no path to award a Vantagem de Ego after character creation |
| "escolha uma Árvore de Magia Natural, pode mimetizar…" (`ElficoFeat.ALMA_FEERICA`, `GorgonaFeat.ABENCOADA_PELO_CONCLAVE`) | mimetizar has no mechanism; the effect is also Forma-gated |
| "escolha duas Formas / Armas Naturais" (`DraconicoFeat.ARMAMENTO_DRACONICO`, `VampiricoFeat.METAMORFOSE_DRACULEA`) | no form state, no weapon catalog to point the pick at |
| "um item escolhido do tipo Escudo" (`EscudeiroFeat.ESPECIALISTA_EM_ESCUDO`) | no Escudo item catalog to choose from |

Each such constant's TODO now names *that* blocker rather than "no choice representation".

### 6.2 `FeatRequirements` cannot gate on another Talento's own choice

`DuelistaFeat.DOMINAR_ARMAS` ("apenas personagens que não escolheram Magias Ofensivas") and
`AssassinoFeat.ACERTO_CRITICO_ARCANO` ("Acerto Crítico Aprimorado (Magias)") both name a
*specific branch* of a prerequisite Talento's pick. `chosenBy` can read it, but
`FeatRequirements` has no hook for "a held Talento's own choice must be / not be X" — every
clause it expresses is about the holder's own stats and traits, not another `Feat`'s payload.

### 6.3 The Margem Crítica margin widens the Menor tier only

`SkillRoll#getCriticalResult(int)`'s margin widens **Acerto Crítico Menor only** — Acerto
Crítico Maior is a literal triple-6, margin-independent. `AcertoCriticoAprimoradoFeat`,
`MAESTRIA_EM_ARMA`, `MESTRE_DE_CACA` and `ARCANISMO_AVASSALADOR` all state "Menor" and are
resolved exactly. A clause that also names the Maior tier (`AssassinoFeat.GOLPE_DE_FINALIZACAO`)
gets its Menor half and nothing for the Maior one; widening Acerto Crítico Maior would need its
own explicit mechanism, which no authored clause has yet.

### 6.4 "Vantagem adicional" is still not distinguishable

Several `PeritoFeat` dependents (`DISCRETO`, `TRABALHO_EM_EQUIPE`, …) grant *"Vantagem
adicional"* — a second Vantagem stacked on a roll that already has one. Nothing records that a
roll is already advantaged, so a second +2 is indistinguishable from a larger flat bonus. Those
constants stay TODO'd on that, not on the (now-solved) chosen-Perícia representation.

# Part II — the Skill Roll protocol

**This is the part that affects a client and an API layer.** Until now a Perícia roll could not
say whether it *succeeded*: `InteractionResult` reported which GD tier the total reached
(`reachedDifficultyLevel`), but nothing told the roll which GD it was made **against**, so no
ability could be gated on the outcome. Combat already did this — `AttackReceiver.resolve` derives
a threshold from `IncomingAttack.getDifficultyLevel()` and compares — a plain Perícia roll had no
equivalent.

---

## 8. Breaking changes

**None.** Every addition is an optional constructor argument or a new getter.

| Type | Added | Consequence for a caller |
|---|---|---|
| `SkillRoll` | 3-arg constructor `(dice, requestedAbility, Integer targetValue)` | none — the 1- and 2-arg forms still compile and behave identically |
| `SkillRoll` | `static SkillRoll against(dice, DifficultyLevel)` | none |
| `SkillRoll` | `Integer getTargetValue()` | none |
| `InteractionResult` | `Boolean getSucceeded()`, `Integer getMargin()` | none — both `null` on a roll that states no target |
| `SkillCompetencyAbility` | `default boolean resolveAutomaticSuccess(SkillType, int, SceneContext)` | none |
| `SkillCompetencyAbility` | `default List<Blessing> resolveSuccessBlessings(SkillType, SkillTrait, SceneContext)` | none |

An existing call site that never supplies a target keeps its exact current behaviour, and
`SkillRollRequest`/`SkillInteractionFactory` needed **no change at all** — the target travels on
the `SkillRoll` a request already carries.

---

## 9. What a client / API must do

### 9.1 Stating the GD

```java
// A GD that is one of the eight tiers — the common case:
SkillRoll roll = SkillRoll.against(List.of(4, 5, 6), DifficultyLevel.MEDIUM);

// A computed GD that lands between tiers ("GD 10 + Vigor"):
SkillRoll roll = new SkillRoll(List.of(4, 5, 6), null, 10 + vigor);
```

The target is a **plain number**, not a `DifficultyLevel`, because not every GD in the rules is a
tier. `SkillRoll.against(...)` resolves a tier to its `getBaseValue()` for you.

### 9.2 Reading the verdict — three states, not two

```java
Boolean succeeded = result.getSucceeded(); // TRUE / FALSE / null
Integer margin    = result.getMargin();    // signed distance from the target; null likewise
```

> **`null` means "no target was stated" — it does not mean "failed".**
> A client that renders `null` as a failure, or an API that serialises it as `false`, will report
> losses that never happened. Every ability inside this core treats `null` as "cannot tell"; a
> consumer must too. If your DTO field is a primitive `boolean`, it needs to become nullable.

### 9.3 Two things you must **not** re-implement

- **Do not subtract `difficultyReduction` yourself.** It is already applied — by easing the
  target that many whole *níveis* before comparing, which is not the same as subtracting it as a
  flat number (a nível is worth a different number of points at each tier).
  `getDifficultyReduction()` is still reported, for display only.
- **Do not treat a low total as a failure.** An ability may make a roll succeed *regardless of
  the dice* (`AttentionCompetencyAbility.PERCEPCAO_DE_FOXM` — "sempre bem-sucedido, dispensando
  rolagens"). Such a roll reports `succeeded == true` with `margin == 0`. Read `getSucceeded()`,
  never recompute from the dice.

### 9.4 A successful roll can now earn Blessings

`result.getBlessings()` may be non-empty on a success — e.g.
`PersuasaoCompetencyAbility.FINTAR_APRIMORADO` grants Vantagem on the next Ataque roll.

They are **reported, not applied**: the Interaction never mutates a sheet, because a `Blessing`'s
`TargetScope` may name someone other than the roller. **A caller that ignores this list silently
drops the effect.** Grant them exactly as you already grant the initiative-time Blessings.

A tie is a success: a total exactly equal to the target beats it, matching `AttackReceiver`'s
existing reading that "a tie is a successful defense".

---

## 10. Migration checklist

1. **Nothing breaks.** Recompile; every existing roll behaves as before and reports
   `succeeded == null`.
2. **Make the verdict nullable end-to-end.** `Boolean`, not `boolean`, in your DTO/JSON schema —
   and make sure the client distinguishes the three states.
3. **Pass the GD when you have one.** Anywhere your API already knows the target GD of a roll
   (a Narrador-set difficulty, a fixed GD in an ability's text), put it on the `SkillRoll`.
4. **Stop deriving success client-side**, if you do. Any local `total >= threshold` check is now
   wrong in two ways: it misses auto-success, and it double-applies `difficultyReduction`.
5. **Consume `getBlessings()` on a successful roll**, or the granted bonus is lost.

## 11. Other consumer-visible additions in this release

Listed for completeness; none is required to act on unless you use the feature. All are additive.

- **Condições / Malefícios** — `sheet.ConditionType` (18 entries) + `sheet.Condition`.
  `CombatantSheet` gains `applyCondition` / `removeCondition` / `hasCondition` /
  `getActiveConditions` / `getConditionBonus`, plus the prohibitions `isMovementPrevented`,
  `isHealingPrevented`, `isAbilityActivationPrevented`, `isSpellCastingPrevented`.
  `SpellCastingService#castSpell` now throws `SPELL_CASTING_PREVENTED` and
  `ActiveAbilityService#activate` `ABILITY_ACTIVATION_PREVENTED` under Silêncio — **two new
  failure modes an API must surface.**
- **Disarming** — `CombatantSheet#disarm(Weapon)` returns the dropped weapon for the caller to
  place (this core models no ground); `rearm(Weapon)` returns `false` when refused;
  `canAttackWith(Weapon)` is a query, not a gate.
- **Drawing and sheathing** — `Character#drawnWeapons` is the in-hand subset of `equipment`, and
  **"utilizando uma arma" now means drawn, not merely carried** (a behaviour change: a sheathed
  blade no longer cancels an unarmed bonus). `WeaponDrawService` is the entry point — `getDrawCost`
  (1PA by default, an Ação Livre for a `SAQUE_RAPIDO` holder), `canDraw`, `draw`, `sheathe` — and
  throws three new keys: `WEAPON_NOT_CARRIED`, `WEAPON_ALREADY_DRAWN`, `WEAPON_DRAW_PREVENTED`.
  **The PA cost is returned, not deducted**; enforcing affordability is the caller's.
- **Movimento Base** — two `CombatantSheet` overloads of `MovementService#getMovementBase`, one
  indexed by which movement of the Rodada it is. Every movement figure is per Ponto de Ação.
- **Dano rolls** — `ModifierType.DAMAGE_ROLL_BONUS`; `InteractionResult#getDamageBonus()` is now
  the **sum** of every source rather than the first non-empty one. A character holding two
  dano-granting traits previously lost one.

# Part III — the per-Rodada action log

## 13. Breaking change

`CombatantSheet#consumeFirstRollThisTurn(AttributeDomain)` **was removed** from the interface. A
direct implementor of `CombatantSheet` (a test double) must drop it; extenders of
`AbstractCombatantSheet` — the expected path, and both `CharacterSheet`/`MonsterSheet` — are
unaffected, they inherit the replacement.

Replacement, all on `CombatantSheet` / `AbstractCombatantSheet`:

| Added | Purpose |
|---|---|
| `void recordAction(CombatantAction)` | the API appends an action it has resolved — **never a side effect of `applyTo`** |
| `List<CombatantAction> getActionsThisRound()` | unmodifiable view of this Rodada's log |
| `void startNewRound()` | clears the log + resets the per-Turn marker; `Scene#next()` calls it on every participant at the Rodada wrap |
| `boolean isFirstRollOfTurnFor(AttributeDomain)` | non-mutating replacement for `consumeFirstRollThisTurn` — reads the slice of the log after the `startTurn` marker |

New value types in `org.aventyrs.core.sheet`: `ActionCost` (`Kind` = `ACTION_POINTS` / `FREE_ACTION` /
`REACTION` + `spentActionPoints()`), `CombatantAction` (`skill`, resolved `governingDomain`,
`attackSource`, `cost`, `turnNumber`, `outcome`), `ActionOutcome` (`ActionOutcome.from(InteractionResult)`).

## 14. What a client / API must do

1. **After resolving a roll** (a bare `AbstractSkillInteraction#applyTo`, or an
   `AttackDelivery`/`AttackReceiver` exchange), build a `CombatantAction` and call
   `sheet.recordAction(...)`. Use `InteractionResult#getGoverningAttributeDomain()` for the
   resolved domain, and the `AttackSource`/`ActionCost` you supplied. `ActionOutcome.from(result)`
   projects the verdict fields.
2. **At each Rodada boundary**, call `sheet.startNewRound()` — or drive the Scene with
   `Scene#next()`, which does it for every participant automatically.
3. **`applyTo` no longer self-consumes** the first-roll-of-Turn flag. If you never call
   `recordAction`, `DexterityAbility#PRECISAO`-style bonuses apply on *every* roll, not just the
   first. Previews (`applyTo` with no follow-up `recordAction`) are now side-effect-free.

## 15. `SkillRoll` gains a 4th constructor arg

`new SkillRoll(dice, requestedAbility, targetValue, ActionCost)`. The 1-/2-/3-arg forms are
unchanged (they delegate with a `null` cost). `actionCost` is metadata — only
`Feat#resolveAttackCostDifficultyReduction` reads it.

## 16. `AssassinoFeat.SAQUE_RELAMPAGO`'s "-1 nível" is real

Through `SaqueRelampagoFeat` (choice-carrying `AbstractFeat`, `WeaponOrSpellChoice` = `WEAPONS` /
`SPELLS`), overriding the new `default int Feat#resolveAttackCostDifficultyReduction(SkillType,
SceneContext, Character, AttackSource, ActionCost, List<CombatantAction>)`. It folds a −1 into
`difficultyReduction` for the first ≤1PA attack of the chosen method each Rodada. Applied via
`DifficultyLevel#easier` on the direct skill-roll path and by `AttackReceiver`; on the
`AttackDelivery` flat-Defesa path it rides `DeliveredAttackResult#getUnappliedDifficultyReduction()`
(the "Open question" that class documents).

## 17. New `TranslatableMessages` key

`INVALID_ACTION_COST` — `ActionCost`'s construction guard (a `FREE_ACTION`/`REACTION` carrying PA,
or an `ACTION_POINTS` cost below 1).

## 18. Per-Cena action log, `Feat` combat hooks, defeat trigger

Follow-up work closing more `AssassinoFeat` gaps:

- **`CombatantSheet` per-Cena state**: `startNewScene()` (`Scene#addParticipant` calls it),
  `getActionsThisCena()` (cleared only by `startNewScene`, not the Rodada wrap),
  `hasDrawnWeaponThisScene()`. `SAQUE_RELAMPAGO`'s Vantagem rider and `ACERTO_CRITICO_RELAMPAGO`
  are real through them.
- **New `Feat` `default` hooks**: `resolveCriticalMarginIncrease(..., CombatantSheet holder)` (a
  6th overload, falls through to the 5-arg); `resolveExtraCriticalEffects(attacker, attackSkill,
  attackSource, criticalResult)` → `List<CriticalEffect>` (`AttackDelivery` merges them —
  `ABRIR_FERIDAS` → `Sangramento`); `resolveDefeatBlessings(attacker, defeated, viaCriticalHit)`
  → `List<Blessing>`.
- **New `DefeatBlessingService`** (`org.aventyrs.core.character.services`) —
  `applyDefeatBlessings(attacker, defeated, viaCriticalHit)`, caller-driven (no defeat observer):
  scans the attacker's `resolveDefeatBlessings` and applies each `Blessing` on the attacker.
  `SANGUE_QUENTE` (+PA on any defeat), `VIOLENCIA_DESCOMUNAL` (+Movimento on a critical
  elimination — the "para se aproximar" direction scoping is dropped), `ARCANISMO_AVASSALADOR`
  (+1 cumulative `DOMINIO_DO_MANA_ROLL_BONUS`, granted for a long Rodada count to approximate
  "até o fim da Cena" — no scene-end trigger exists).
- **Prerequisites now enforced** via per-constant `isEligible` overrides: `SAQUE_RELAMPAGO`'s
  "ou Foco 5" disjunction, `ACERTO_CRITICO_ARCANO`/`ACERTO_CRITICO_RELAMPAGO`'s "Acerto Crítico
  Aprimorado (Magias/weapon)" choice-prereq, `ESPECIALISTA_TECNOLOGICO`'s Profissão-4 +
  Especialização Mecânica.

Still large / not done: `GOLPE_SOBRENATURAL`/`GOLPE_SOMBRA_SOBRENATURAL` (PV/PM spend

## 20. Magia acquisition now costs XP — Part IV

`SpellService#grantSpell` used to spend nothing. It now spends
`getAcquisitionCost(character, spell)` before mutating — same validate→spend→grant order as
`FeatService#grantFeat`, and it throws `NOT_ENOUGH_EXPERIENCE` (an existing key) when the sheet
can't pay.

### 20.1 Breaking changes

| Interface | Added | Consequence for an outside implementor |
|---|---|---|
| `SpellService` | `Set<SpellTree> getKnownTrees(Character)` | **must implement** |
| `SpellService` | `BigDecimal getAcquisitionCost(Character, Spell)` | **must implement** |
| `Feat` | `default boolean grantsFreeSpellAcquisition(Character, Spell)` → `false` | none |
| `Feat` | `default BigDecimal resolveSpellAcquisitionCostReduction(Character, Spell)` → `ZERO` | none |
| `Race` | `default BigDecimal resolveSpellAcquisitionCostReduction(Character, Spell)` → `ZERO` | none |

A caller of `SpellServiceImpl` needs no change beyond funding the `CharacterSheet` — a
`grantSpell` for a Broto+ Magia onto a sheet with too little XP now fails where it used to pass.

### 20.2 What's new

- **`SpellService.ACQUISITION_EXPERIENCE_COST`** — `Map<BranchLevel, BigDecimal>`, `0 / 1 / 2 /
  3 / 5` for SEMENTE / BROTO / MUDA / EMERGENTE / FLORESCENTE. The four deeper figures are the
  `MetamagicoFeat` ladder's "ao custo de N exp" clauses (the ruleset's only stated spell price);
  SEMENTE-free is an inference. `BigDecimal` so a future fractional discount fits.
- **`SpellService#getKnownTrees`** — the distinct `SpellTree`s over `character.getSpells()`. In
  this core, *conhecer* an Árvore is simply holding one of its Magias. Derived, not stored. This
  is what `MetamagicoFeat#ARCANISTA`'s "conhece N Árvores de Magia" is read against.
- **`SpellService#getAcquisitionCost`** — the full price a `grantSpell` will charge: `ZERO` if a
  held Talento grants the Magia (`grantsFreeSpellAcquisition`, checked first), else the rung
  price minus every `Feat#resolveSpellAcquisitionCostReduction` **and** the
  `Race#resolveSpellAcquisitionCostReduction`, summed and floored at zero. A UI pricing
  acquisition must call this, not the map.
- **`Feat#grantsFreeSpellAcquisition(Character, Spell)`** — wired ahead of its first consumer.
  `MetamagicoFeat#ARCANISTA` will override it once it has an acquisition-time-choice class.
- **`Feat` / `Race` `resolveSpellAcquisitionCostReduction(Character, Spell)` → `BigDecimal`** —
  the partial-discount hooks the aggregation sums. Live consumer: **`Agastias`' "Magia é
  Ciência"** (−0.5 EXP on every Magia, unscoped). Pending: `ElementalFeat#ARCANISMO_ELEMENTAL`
  and the `Furia`/`NascidoDaFloresta` "Natural" clauses (still need element/type scoping).

### 20.3 Still not done

`ARCANISTA`'s choice class (the N-tree / 2-Broto-tree picks), its auto-learning loop
("Sementes automaticamente aprendidas" has no loop), and `ElementalFeat#ARCANISMO_ELEMENTAL` /
`Furia` / `NascidoDaFloresta`, whose discounts are scoped to "seu elemento" / "Naturais" — the
hook exists, but there's no per-Magia element column (type is checkable via `Spell#getPrimaryType`)
and those racial abilities aren't modelled as constants at all. RM is untouched.

## 21. A Magia's primary damage — Part V

The first spell *effects* become computable. `SpellData` gains a nullable `primaryDamage`
column and `SpellCastingService` resolves it against a caster. Nothing is applied — this is
report-only, the same shape as `AttackDelivery`.

### 21.1 Breaking changes

| Interface | Added | Consequence for an outside implementor |
|---|---|---|
| `SpellCastingService` | `Optional<ResolvedSpellDamage> resolvePrimaryDamage(Spell, CombatantSheet)` | **must implement** |
| `Spell` | `default Optional<SpellDamage> getPrimaryDamage()` → empty | none |
| `AttributeAbility` | `default boolean upgradesFirstSpellOfRoundFocusScaling()` → false | none |

`SpellCastingResult` gains a nullable `primaryDamage` field (builder-only class, additive).

### 21.2 What's new

- **`SpellDamage`** (`org.aventyrs.core.magic`) — a record `(int diceCount, int flatBonus,
  FocusScaling focusScaling, DamageType damageType, ElementalType elementalType)`, the structured
  form of *"Causa 2d6+Metade do Foco pontos de Dano Mágico Elemental: Magma"*. Type/element
  pairing validated like `DamageBonus`. `"Dano Mágico Elemental: X"` and bare `"Dano Elemental:
  X"` both map to `DamageType.ELEMENTAL` (no `MAGICO_ELEMENTAL` constant).
- **`FocusScaling`** — `NONE` / `HALF` / `FULL`. `HALF` is the only authored value.
- **`SpellCastingService#resolvePrimaryDamage`** — computes the deterministic part (`flatBonus` +
  Foco term) into a **`ResolvedSpellDamage`** (`deterministicAmount`, `diceCount`, type, element,
  `focusFullyApplied`). The `diceCount` d6 stay the caller's to roll — this core never rolls.
  `castSpell` puts the result on `SpellCastingResult#getPrimaryDamage()`.
- **`FocusAbility.MAGIA_PODEROSA` is real for these Magias** — `resolvePrimaryDamage` upgrades a
  `HALF` term to full Foco when the caster has cast no Magia yet this Rodada (no `Spell` in
  `getActionsThisRound()`) and holds an ability with
  `AttributeAbility#upgradesFirstSpellOfRoundFocusScaling()` true. Relies on the API recording
  each cast as a `CombatantAction` with the `Spell` as its `attackSource`.
- **Authored:** `IraDeVulcanoSpell` (Sopro de Magma Menor/Maior, Torrente Vulcânica, Ira de
  Vulcano primary) and `PiromanciaSpell` (Hálito de Eldur, Bola de Fogo Elduriana, Olhar de
  Eldur). All `HALF` Foco.

### 21.3 Still not done

`SpellDamage` holds no distance falloff, recurring cadence, delayed wave, off-target damage, or
*healing* — each stays prose on the constant. `castSpell` still resolves neither roll's
success/failure (no target-GD comparison). `FocusAbility.MAGIA_PODEROSA` stays prose for any
Magia without a `SpellDamage`.

## 22. One attack, several targets — Part VI

`AttackDelivery` used to resolve exactly one defender. It can now resolve an attack that reaches
several, driven by the first Talento that grants one —
`ArtesMarciaisFeat.DOMINAR_ARTE_MARCIAL_ARTE_FLUIDA` ("Enquanto não estiver utilizando nenhuma
arma - exceto Armas Naturais - e nenhum item do tipo Escudo seus ataques afetam um alvo
adicional"), which is now fully real. Still report-only: nothing is applied, the same shape as
every other `AttackDelivery` outcome.

The rule that shapes the whole design is that **one attack is one roll and one dano roll**. The
extra targets change *what the total is compared against* and *how much of the damage lands* —
never how many times the dice are read.

### 22.1 Breaking changes

| Interface | Added | Consequence for an outside implementor |
|---|---|---|
| `DamageService` | `int calculateFinalDamage(CombatantSheet, SceneContext, DamageType, CombatantSheet, int, boolean, boolean halfDamage)` | **must implement** |
| `AttackTargetingService` | the whole interface (new) | implement only to replace `AttackTargetingServiceImpl` |
| `Feat` | `default int resolveAdditionalTargets(SkillType, Character)` → `0` | none |
| `Feat` | `default Optional<DamageBonus> resolveDamageBonus(SkillType, SceneContext, CombatantSheet, Character, AttackSource, int targetCount)` → delegates to the 5-arg form | none |
| `AbstractSkillInteraction` | `applyTo(CombatantSheet, SceneContext, SkillRoll, CombatantSheet, AttackSource, List<CombatantSheet>)` | see the warning below |

**⚠ A subclass of `AbstractSkillInteraction` that overrides the 5-arg `applyTo` must move its
override to the new 6-arg form.** The 5-arg overload is now a pure delegator, so an override left
on it still compiles and is still reached by short-form callers — but is **silently bypassed** by
anything calling the longest form, which includes every `AttackDelivery#resolve`. This is the
same "override the longest overload" rule that already governed this class; the longest one just
moved. `ArtesInteraction` was moved accordingly. `EsquivaEApararInteraction` is unaffected — its
4-arg override takes a `DefenseType`, a different overload family.

`attackTarget` is deliberately **not** widened into a list. It stays the *primary* target, and the
extras are a trailing parameter, for two reasons: every target-conditioned hook still resolves
against the primary alone (below), and widening it would have made a plain
`applyTo(t, ctx, roll, null, null)` call ambiguous at the call site.

### 22.2 What's new

- **`AttackTargetingService#getMaximumTargets(Character attacker, SkillType attackSkill)`** —
  `BASE_TARGETS` (1) plus every held `Feat#resolveAdditionalTargets`, never below 1. **A UI showing
  a player how many foes they may pick must call this**, and each Talento checks its own conditions
  inside the hook, so the answer already reflects what the character is currently wielding.
- **`DeliveredAttack#additionalTargets`** — a `@Singular List<AttackTarget>`, where
  **`AttackTarget`** is a `record (CombatantSheet defender, int defenseValue)` with an
  `AttackTarget.of(MonsterSheet, DefenseType)` convenience mirroring `DeliveredAttack.from`. A
  Defesa per target because it is each defender's own stat; the `DefenseType` stays shared on
  `DeliveredAttack`, since one blow is resisted the same way by everyone it reaches.
- **`AttackDelivery#resolve` refuses an over-wide attack** — more targets than
  `getMaximumTargets` allows throws `IllegalOperationException(TOO_MANY_ATTACK_TARGETS)`. A cap
  enforced on the service entry point that applies it, like every other cap in this core.
- **`DeliveredAttackResult#additionalTargetResults`** — one **`DeliveredAttackTargetResult`** per
  additional target, in the order supplied, carrying `defender` / `requiredTotal` / `margin` /
  `hit` / `criticalEffectTriggered` / `effectChainTriggered` / `nextInteraction`. The **primary
  target keeps the flat fields it always had**, so every existing single-target caller reads
  exactly what it read before and the list is simply empty.
- **What is judged per target, and what isn't.** The roll happens once (rolling twice would
  double-grant the critical-success Ego point), so one `attackTotal` and one `CriticalResult` cover
  every target. Per target: the margin, whether it landed, whether it cleared *that* defender's
  Corrente threshold, and which Efeitos Críticos *their* anatomy admits
  (`CriticalEffect#applicableTo` is now run per defender).
- **`DamageInteraction#halvingDamage()`** — a fluent marker, the sibling of `chainInto`, set by
  `AttackDelivery` on the chain head of every additional target and never on the primary's. It is
  the first **attacker-side** Meio-Dano in this core: every other half-damage source belongs to
  whoever is being hit. It reaches the new `DamageService#calculateFinalDamage(…, boolean
  halfDamage)`, which **OR**s it into the target's own `ModifierType.HALF_DAMAGE` /
  `EgoAdvantage#resolveHalfDamage` sources — so it still applies **last**, after RD and RA, and two
  half-damage sources never quarter a blow.
- **`Feat#resolveDamageBonus(…, int targetCount)`** — for a clause conditioned on *how many*
  targets the one dano roll covers. `targetCount` is the primary plus the extras, and **`0` means
  no target was named at all** (the bonuses-only preview path), which an override must read as
  "condition not met" rather than as "one target".
- **`ArtesMarciaisFeat.DOMINAR_ARTE_MARCIAL_ARTE_FLUIDA` is live**, all three halves: the extra
  target, a flat `Skill.DISADVANTAGE_MALUS` on the dano roll while more than one target is named,
  and Meio-Dano on the additional target. Both gates ("nenhuma arma exceto Armas Naturais" reads
  *drawn* weapons, not merely carried ones; "nenhum item do tipo Escudo" reads `getEquipment()`)
  are checked by both hooks, so the extra target and its Desvantagem can never disagree.

### 22.3 What a client / API must do

```java
DeliveredAttackResult result = new AttackDelivery().resolve(DeliveredAttack.from(primaryFoe, DefenseType.PHYSICAL)
        .attacker(attackerSheet)
        .attackSkill(SkillType.ATAQUE_CORPO_A_CORPO)
        .attackRoll(new SkillRoll(List.of(4, 5, 3)))
        .additionalTarget(AttackTarget.of(secondFoe, DefenseType.PHYSICAL))   // ← the UI picked this one
        .build());

int danoRoll = rollDamageOnce();          // one attack, one dano roll
if (Boolean.TRUE.equals(result.getHit())) {
    drain(result.getAttackResult().getNextInteraction(), primaryFoe, danoRoll);
}
for (DeliveredAttackTargetResult extra : result.getAdditionalTargetResults()) {
    if (Boolean.TRUE.equals(extra.getHit())) {
        drain(extra.getNextInteraction(), extra.getDefender(), danoRoll);   // same figure — it halves inside
    }
}
```

Two obligations, both on the caller:

1. **Pick the targets.** Every clause granting an extra target also requires it to be *adjacent to
   the primary one*. That is pairwise geometry between two combatants who are both **not** the
   roller, and a `SceneContext` holds distances measured only from its own holder — so this core
   cannot check it and does not pretend to. **It enforces how many, never which ones.** Call
   `getMaximumTargets` to bound the selection UI.
2. **Feed the same dano figure to every chain.** Do not pre-halve anything for the additional
   target: `halvingDamage()` is applied after RD and RA, and halving the input instead would
   subtract mitigation from an already-halved number.

### 22.4 Still not done

- **Target-conditioned hooks still see the primary target only** — `resolveDamageBonus`'s
  `attackTarget`, `SkillCompetencyAbility#resolveAttackRollBonus` (`FRIEZA`,
  `ABATEDORES_DE_GIGANTES`). Recomputing them per target would need a per-target
  `InteractionResult`, and no authored trait asks for one: the rules scope the extra targets to the
  comparison and the damage, not to the bonuses.
- **Meio-Dano on *every* target including the primary has no expression.**
  `CavalariaFeat#ATAQUE_EM_ARCO`'s "o valor dos danos causados em cada alvo é igual a metade do
  valor rolado" needs it — that constant is otherwise unblocked by this release and now cites only
  its remaining blockers (a montaria/veículo concept, and "apenas ataques físicos", which needs the
  delivery path to carry the attack's `DamageType`).
- **`AttackReceiver` has no counterpart**, deliberately: a foe attacking the player is one foe
  against one roller.
- **Área de Efeito is still a different, unbuilt thing.** `scene.AreaOfEffect` describes a
  footprint; nothing resolves one into a set of targets, and neither entry point classifies an
  incoming attack as an area one — `EsquivaEApararCompetencyAbility#EVASAO` remains blocked.
- No `SkillCompetencyAbility` / `AttributeAbility` counterpart to `resolveAdditionalTargets`; add
  one with its first real consumer.
