# Changelog — aventyrs-core 0.0.20

Written for projects that consume this library. Everything below is the delta since commit
`c4ad856` ("feat: Enable Scene state persistence and dynamic participant changes"), which is the
whole of this version's work and is currently uncommitted in the tree.

`build.gradle` declares `version '0.0.20'`.

> **Note on 0.0.19.** There is no `0.019.CHANGELOG.md`. Version 0.0.19 was the Scene
> state-persistence work in `c4ad856`, and it shipped without one — so `0.018.CHANGELOG.md` plus
> this file together leave that one commit undocumented. This file deliberately does **not**
> absorb it: describing a range this version didn't touch would misattribute it. If you are
> upgrading from 0.0.18 rather than 0.0.19, read `c4ad856` directly.

This version has one theme: **a foe can be summoned, and its stat block can say what its anatomy
refuses.** The Zumbi is the first creature whose numbers depend on who called it up, and the
first whose Anatomia clause is enforced rather than described.

`./gradlew test` passes on the current tree — 1567 tests — apart from two pre-existing failures
unrelated to this range (see §6.1).

---

## 1. Breaking changes

**None.** Every addition below is a defaulted interface method, a new type, or a new overload.
Existing `MonsterTemplate` implementations, `AbstractMonsterTemplate` builders and `MonsterSheet`
call sites compile and behave unchanged.

One thing to know if you implement `CriticalEffect` **outside** this library: it gained an
abstract `getType()` (§2.3). Nothing in either downstream consumer does, so this is listed here
rather than in a migration step.

---

## 2. New features

### 2.1 Summoning a Zumbi

`org.aventyrs.core.monster.summon.Zumbi` is the first invocação — a corpse animated by a
Conjurador, whose stat block reads *"se você possuir N ou mais Graduações em Domínio do Mana…"*
throughout. **Three ways in**, in decreasing order of how much the caller knows:

```java
import org.aventyrs.core.monster.MonsterSheet;
import org.aventyrs.core.monster.summon.Zumbi;

// 1. A player character cast the Magia. Reads their Graduação in Domínio do Mana off their sheet.
MonsterSheet raised = Zumbi.builder().build().spawn(necromancer);   // necromancer is a Character

// 2. The Narrador is running it from a form, and typed a number into the field.
MonsterSheet fromForm = Zumbi.summonedBy(7).spawn();

// 3. Nobody summoned it — it's in the scene for narrative reasons.
MonsterSheet shambler = Zumbi.builder().build().spawn();
```

Choose the corpse it animates, and re-parameterize a template you already hold:

```java
MonsterSheet ogreCorpse = Zumbi.builder()
        .bodySizeCategory(SizeCategory.PLUS_ONE)   // clamped to MINUS_TWO..PLUS_TWO
        .build()
        .spawn(10);

Zumbi catalogEntry = Zumbi.builder().bodySizeCategory(SizeCategory.MINUS_ONE).build();
Zumbi thisOne      = catalogEntry.withConjurador(4);   // a copy; catalogEntry is untouched
```

Then put it in a scene the ordinary way — `Scene#addParticipant` is typed `CombatantSheet`, and
there is no monster-specific entry point:

```java
Scene scene = new Scene();
scene.setCombatScene(true);
UUID party = UUID.randomUUID();
UUID foes  = UUID.randomUUID();

scene.addParticipant(hero, 14, party);
scene.addParticipant(Zumbi.summonedBy(10).spawn(), 6, foes);
```

**What each spawn produces**, at Vigor 2 / Força 4 / Ataque Corpo-a-Corpo `[Primal]` 2, DF and DM
both 11, 2 PA, `lifeMultiplier` 5:

| Conjurador's Graduação | What changes |
|---|---|
| any, including 0 | Vantagem on Perícias de Ataque against a **living** target |
| any | Bônus em Perícia de Ataque equal to the Graduação — see §2.2 for why this lands twice |
| ≥ 4 | +10 PV (Bônus Mágico, encantamento) — 20 PV becomes 30 |
| ≥ 7 | +2 Força (so 6) **and** Roubo de Vida 1 |
| = 10 | GD de Perícias reduced by one nível |

`0` is a real, meaningful value here, not a null stand-in: it's the untiered baseline every
"se você possuir N ou mais" clause measures up from. A Conjurador untrained in Domínio do Mana
produces exactly the same creature as `spawn()` with no Conjurador at all.

Every spawn is fully independent, as for any `MonsterTemplate` — its own identity, resource
pools, `SkillGraduation` instances, and now its own `LifeSteal`.

### 2.2 `SummonedMonsterTemplate`

```java
int getConjuradorManaGraduation();                          // 0 = nobody summoned it
SummonedMonsterTemplate withConjurador(int manaGraduation);  // returns a copy
default MonsterSheet spawn(int manaGraduation);
default MonsterSheet spawn(Character conjurador);
static int manaGraduationOf(Character conjurador);           // 0 if untrained or null
```

**The parameter is a plain `int`, not a summoner entity.** Every clause of this shape keys off
exactly one number — the Conjurador's Graduação in Domínio do Mana — so that number *is* the
parameter. Modelling a Conjurador↔invocação relationship would mean inventing something nothing
else in this core uses, and would make the commonest case impossible: a Narrador placing a Zumbi
has no summoner object, only a number they picked, or none.

**`withConjurador` returns a copy** rather than mutating. The tier bonuses reach into the
creature's Attributes, its abilities and its authored `attackBonus` — all of which
`MonsterTemplate#spawn()` reads off the template *before* building the `Character` — so the
Graduação must be known before spawning, not applied to the sheet afterwards. Returning a copy
keeps a catalog entry immutable and shareable: two Conjuradores summoning from the same template
cannot disturb each other's numbers.

**One clause can need two consumers.** The Zumbi's attack bonus is both a `@Modifier` on its
ability (raising the Zumbi's *own* Ataque roll, via `AttackDelivery`) and the template's
`getAttackBonus()` (raising the threshold its attack presents when the *defender* rolls, via
`AttackReceiver`). Same clause, opposite directions of the exchange.

Tiered numbers are possible at all because `ModifierResolver` invokes `@Modifier` methods **on
the source instance** — so a no-arg annotated method can return an instance field. The
annotation's `ModifierType` stays compile-time-fixed; only the returned value varies. This is
`ArtesAprimorarComArteAbility`'s existing pattern; `ZumbiAbility` is the second user of it.

### 2.3 Efeito Crítico immunity — `CriticalEffectType` and `CriticalEffect#applicableTo`

An Anatomia clause naming Efeitos Críticos a creature shrugs off is now real, enforced data. It
was previously impossible: nothing anywhere could exclude a target from an Efeito Crítico
(`VigorAbility.RECUPERACAO_ASSOMBROSA`, `AbracadoPelaEscuridaoAbility` and
`ProfissaoCompetencyAbility` all TODO'd it).

```java
// org.aventyrs.core.effect
public enum CriticalEffectType {
    SANGRAMENTO, PURGA_DE_MANA, PRIMOR, SABOTAGEM, EXECUCAO_REAL,   // implemented
    AMALDICOAR, DILACERAR, EXCRUCIANTE, FERIDA_PROFUNDA             // named only
}

CriticalEffectType CriticalEffect#getType();
static List<CriticalEffect> CriticalEffect.applicableTo(CombatantSheet target,
                                                        List<CriticalEffect> effects);
Set<CriticalEffectType> CombatantSheet#getCriticalEffectImmunities();  // empty by default
```

**Keyed on an enum, not on `Class<? extends CriticalEffect>`.** Four of the five effects a Zumbi
resists have no implementation in this core. Keyed on a class, those immunities would be
inexpressible until someone built the effect, and a stat block would have to lie by omission
meanwhile. Keyed on the enum they are exact, authored data now — and correct the day the effect
lands, with nothing to revisit.

**The filter lives on `CriticalEffect`, not in either attack entry point.** `AttackDelivery` and
`AttackReceiver` both route their `criticalEffects` through the one static method. An immunity is
a fact about the *victim*, identical whichever direction is running; writing it into one entry
point would leave the other silently wrong. That symmetry is not hypothetical — a summoned
creature acts on its summoner's roll, so a player can drive either side of an exchange against a
foe whose anatomy resists part of what lands.

**It filters, it does not throw.** A caller assembling an attack has no obligation to know what
its target resists, and an attack that crits against an immune target is still a critical hit —
it just produces a shorter chain.

### 2.4 Four new `MonsterTemplate` hooks

All defaulted, so every existing foe is unchanged:

| Hook | Default | Answers |
|---|---|---|
| `getActionPoints()` | `ActionPointsService.DEFAULT_ACTION_POINTS` (3) | "Possuem 2 Pontos de Ação (PA)" |
| `getSkillSpecializations()` | `Map.of()` | the bracketed tag — `Ataque Corpo-a-Corpo [Primal]` |
| `isUndead()` | `false` | Anatomia de Morto-Vivo |
| `getCriticalEffectImmunities()` | `Set.of()` | "Imunes aos Efeitos Críticos …" |

Builder calls on `AbstractMonsterTemplate`: `.actionPoints(2)`,
`.skillSpecialization(TYPE, List.of(...))`, `.undead(true)`,
`.criticalEffectImmunity(CriticalEffectType.SANGRAMENTO)`.

An Especialização naming a Perícia the foe has no Graduação in is silently ignored — `spawn()`
iterates the Graduações.

### 2.5 `MonsterSheet.of(Character, MonsterTemplate)`

Two new factories, alongside the two existing positional ones (unchanged):

```java
static MonsterSheet of(Character character, MonsterTemplate template);
static MonsterSheet of(Character character, MonsterTemplate template, UUID id);  // restore path
```

`spawn()` now uses the first. The anatomy halves are as authored as the four combat numbers, and
folding them into the positional overload would have produced an eight-argument signature no
call site could read. The positional overloads still exist for hand-built sheets and default to
`undead = false` with no immunities.

### 2.6 `ModifierType.HIT_POINTS` and `HitPointsService#getHitPointsBonus`

```java
int getHitPointsBonus(Character character);
// getMaxHitPoints is now:
//   BASE_HIT_POINTS + Vigor.getTotal() * lifeMultiplier + getHitPointsBonus(character)
```

The **flat** PV grant — the "recebe Bônus Mágico (encantamento) de +10PV" shape, whose amount its
rules text states outright. Not interchangeable with `LIFE_MULTIPLIER`: a multiplier scales with
Vigor, so a stated number expressed as a multiplier uplift only lands correctly at one specific
Vigor. (For the Zumbi, `lifeMultiplier` 5 → 10 *would* have produced exactly +10 PV — but only
because its Vigor happens to be 2, and it would be wrong for anything else reusing the mechanism.)

`getHitPointsBonus` scans `attributeAbilities` **and** `SkillCompetencyAbility.allFor` (so racial
and monster-authored traits count). `getLifeMultiplier` deliberately still scans only the former:
widening it would change a computed total nothing asked to change. Neither scans
`SkillExcellency` tiers.

## 3. Behavior changes (no signature change)

### 3.1 `getMaxHitPoints` gains a third term

See §2.6. No existing ability grants `ModifierType.HIT_POINTS`, so every pre-existing character's
maximum is arithmetically identical; the term is 0 for all of them.

### 3.2 An attack's Efeitos Críticos may now be dropped before the chain is built

See §2.3. `AttackDelivery`/`AttackReceiver` still report `criticalEffectTriggered` exactly as
before — the crit happened — but the chain behind the head `DamageInteraction` no longer contains
effects the defender is immune to. Every combatant in 0.0.19 was immune to nothing, so no
pre-existing behaviour changes.

## 5. Migration checklist

Nothing is required. Optional, in order of likely interest:

1. If you present monsters in a UI, `MonsterSheet#isUndead()` and
   `#getCriticalEffectImmunities()` are new display data.
2. If you build foes, consider `.actionPoints(...)` and `.skillSpecialization(...)` for stat
   blocks that state them — previously those clauses had to be dropped.
3. If you implement `CriticalEffect` outside this library, implement `getType()`.
4. If you grant a stated flat PV bonus by inflating `lifeMultiplier`, switch it to
   `@Modifier(ModifierType.HIT_POINTS)` — the old approach is only correct at one Vigor.

## 6. Known issues and deliberate gaps

### 6.1 Carried forward from 0.0.18

The same two pre-existing test failures, unrelated to this range and still unaddressed:
`SizeCategoryTest#shiftClampsAtThePlusFourCeiling` and
`CharacterSizeServiceTest#bonusIsClampedAtThePlusFourCeiling`. Both concern `SizeCategory#shift`
clamping to the full 15-value array while its javadoc claims a -4/+4 range.

### 6.2 "Living" is `isUndead()` inverted, and that is a stand-in

`ZumbiAbility` resolves *"contra personagens vivos"* as "the target is not a foe that declared
itself Morto-Vivo". That is **exact for every combatant this core can currently build** — a
`CharacterSheet` is always a living character, and the only non-living things are foes that say
so — but it is not the real classification. `CreatureType` has only HUMANOIDE/FEERICO/MONSTRUOSO,
none of which is about vitality. The day a player character can be undead, or a construct or
elemental must count as non-living without being a Morto-Vivo, this needs a real anatomy tag on
`Character`. Do not reach for `isUndead()` as a general-purpose vitality flag.

### 6.3 A summon cannot yet act on its summoner's roll

`SummonedMonsterTemplate` builds the creature; nothing models the player then *rolling for it*.
`AttackDelivery` assumes the roller is the attacker and `AttackReceiver` that they are the
defender, and neither has a notion of rolling on a third combatant's behalf. This gap is why
§2.3's filter is shared between both directions rather than written into either — that much is
correct regardless of who holds the dice.

### 6.4 Four Zumbi clauses have no mechanism

Each blocked on a different missing system, each TODO'd on the class rather than guessed at:

- **"Imunes a danos Profanos e Naturais"** and **"Danos Físicos de Esmagamento reduzidos em -3"**
  — `DamageType` has no Profano, Natural or Esmagamento constant, and `DamageService` resolves
  RD/RA with no notion of the incoming damage's type. The sole existing exception,
  `AttributeAbility#resolveDamageReduction`, is unreachable from a `SkillCompetencyAbility`. The
  -3 needs the type-scoped half; the two immunities need a nullification stage that exists in no
  form. **Note the asymmetry with §2.3**: *critical-effect* immunity is now real; *damage-type*
  immunity is not.
- **"Não precisam dormir ou respirar"** — nothing tracks fadiga or asfixia, so there is no effect
  to be exempt from.
- **"Sofrem Danos de Magias Divinas que recuperam PV"** — needs both a `Magia` entity carrying a
  Tipo (none exists; `SpellCastingService` cannot resolve either roll's GD for the same reason)
  and an inversion stage on healing, which `CombatantSheet#heal` has no hook for.
- **"Danos de Ataques 1d6+3 (Base 1 + Metade da Força)"** — a foe's damage is entirely
  caller-supplied. This core has no weapon or dano-roll concept and never rolls dice, so
  `AttackDelivery`/`AttackReceiver` assemble a `DamageInteraction` and the caller feeds it the
  figure. The formula is recorded in the Zumbi's javadoc rather than dropped.

### 6.5 Two authored numbers are judgement, not text

The Zumbi's stat block states both *"Bônus Racial de +5 em Defesas"* and, under Outras
Informações, *"Defesas +6"*. These are read as stacking: **DF 11 / DM 11**. And the block states
no Grau de Dificuldade for the Zumbi's own attacks, so `getAttackDifficulty()` returns
`DifficultyLevel.EASY` as a catalogue judgement for a creature this weak. Separately,
*"Ataque Corpo-a-Corpo [Primal] +2"* is read as a Graduação of 2. Correct any of the three by
editing the constants on `Zumbi`; `ZumbiTest#everyStatBlockConstantMatchesTheRulesText` pins them.

### 6.6 The Efeito Crítico catalog is not exhaustive

`CriticalEffectType` names only what some piece of authored data in this core needs to name — the
five a Zumbi resists, plus the four already implemented. It is **not** a catalog of every Efeito
Crítico the game has. Add a constant when something names it, not for completeness, and say in
its javadoc whether anything implements it.

### 6.7 Nothing drives the Scene loop

Unchanged from 0.0.18 and still worth stating: `Scene#next()` — and therefore `finishTurn()` and
`tickTemporaryEffects()` — has no production caller in either downstream consumer. A Zumbi's
Roubo de Vida is open-ended and does not depend on the loop, but anything Rodada-scoped does.
