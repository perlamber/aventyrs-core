# Changelog — aventyrs-core 0.0.32

Written for projects that consume this library. One theme: **`Scene` gains an explicit start of
combat, and a Rodada now only elapses inside combat.**

`./gradlew test` passes (`build -x javadoc` green). ~5 new tests; ~12 existing combat/scene
tests migrated to call `startCombat()`.

**One source-breaking removal** (§1) and **one new abstract `CombatantSheet` method** (§2).
No `Feat` / `AventyrTitle` change.

---

## 1. Breaking changes

| Removed / changed | Migration |
|---|---|
| **`CombatStartBlessingService` / `CombatStartBlessingServiceImpl` deleted** (added in 0.0.31) | Call `combatantSheet.startCombat()` — same effect, returns the same `List<Blessing>`. Or `scene.startCombat()` to fire it for a whole Scene at once. |
| **`CombatantSheet` gains abstract `List<Blessing> startCombat()`** | A direct implementor of `CombatantSheet` (a test double) must add it. Extenders of `AbstractCombatantSheet` — the expected path, and both `CharacterSheet`/`MonsterSheet` — inherit it. |
| **`Scene#next()` no longer advances `getCurrentRound()` unless `isCombatScene()`** | Behaviour change, no signature change. See §3. |

New `TranslatableMessages` key: **`SCENE_ALREADY_IN_COMBAT`** (thrown by `Scene#startCombat()`).

The `Feat#resolveCombatStartBlessings(Character)` hook and `AnaoFeat#VIGOR_DO_INVERNO`'s two
Blessings (RD + `ModifierType.CRITICAL_RESISTANCE`, ½ Multiplicador de PV Rodadas) are
**unchanged** — only the thing that fires them moved.

## 2. `CombatantSheet#startCombat()`

```java
List<Blessing> granted = combatantSheet.startCombat();
```

The sheet scans its own `Character`'s Talentos for `Feat#resolveCombatStartBlessings`, applies
each `Blessing` as a `TemporaryBonus` on itself, and returns them. This is where the
0.0.31 `CombatStartBlessingService` logic now lives — a sheet acting on its own `Character`,
like every other resolve pass it already runs.

**Idempotent within a Cena.** A second call before the next `startNewScene()` grants nothing
and returns an empty list, so an orchestrator (`Scene#startCombat()`) and a direct caller can't
double-apply. `startNewScene()` re-arms it. Unlike the initiative-win Blessings
`Scene#applyInitiativeBlessings` tracks, these are never revoked — they just count down.

## 3. `Scene#startCombat()`, and the Rodada gate

```java
Map<CombatantSheet, List<Blessing>> grantedByParticipant = scene.startCombat();
```

Turns `isCombatScene()` on **and** calls `startCombat()` on every participant — those in the
rotation and those still pending alike — returning what each was granted (keyed by sheet in
initiative order, participants granted nothing omitted). Throws
`IllegalOperationException(SCENE_ALREADY_IN_COMBAT)` on an already-combat Scene.

Like `applyInitiativeBlessings`, `Scene` does not reach into a Service to resolve what abilities
grant — each `CombatantSheet` resolves its own. `setCombatScene(boolean)` stays as the bare
flag mutator for a Scene rebuilt from persistence already mid-combat (alongside
`restoreTurnCursor`).

**`Scene#getCurrentRound()` now only advances while `isCombatScene()` is true.** `next()` still
cycles the turn cursor before combat, but the wrap:

- leaves `currentRound` at **0**, and
- fires **no Rodada boundary** — no `pendingEntries` merge, no initiative re-sort, no per-Rodada
  action-log clear (`CombatantSheet#startNewRound()`), no `ActiveAreaSpellEffect` tick.

A Rodada is a combat unit; nothing about it elapses outside combat.

## 4. What a client / API must do

1. **Call `scene.startCombat()` when combat breaks out** — instead of
   `new CombatStartBlessingServiceImpl().applyCombatStartBlessings(sheet)` per participant, or
   `scene.setCombatScene(true)`. It does both jobs (flag + triggers) in one call.
2. **A Scene rebuilt already mid-combat** keeps using `setCombatScene(true)` +
   `restoreTurnCursor(round, index)` — that path does not re-fire combat-start triggers, by design.
3. **If you drive turn order with `next()` before combat has started**, expect `getCurrentRound()`
   to stay 0 and the per-Rodada bookkeeping not to run until `startCombat()`. In practice `next()`
   is a combat loop, so start combat first.
4. **A test or fixture that builds a `Scene` and calls `next()` expecting a round to elapse** must
   now call `scene.startCombat()` (or `setCombatScene(true)`) after adding participants.
