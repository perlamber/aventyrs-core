# Changelog — aventyrs-core 0.0.33

Written for projects that consume this library. One theme: **`Scene` gains a passive 4-way
adjacency map — each Scene can name a neighbour Scene to its north / south / east / west by id —
and can now be reconstructed with a saved identity.**

`./gradlew build -x javadoc` passes. ~18 new tests (`SceneTest`, `DirectionTest`).

**No breaking changes.** One new enum, four new `Scene` methods, one new `Scene` constructor. No
`Feat` / `AventyrTitle` / `SceneContext` / `TranslatableMessages` change. The existing no-arg
`new Scene()` is unchanged.

---

## 1. `Direction`

New enum in `org.aventyrs.core.scene`: `NORTH`, `SOUTH`, `EAST`, `WEST`, with

```java
Direction opposite();   // NORTH<->SOUTH, EAST<->WEST; its own inverse
```

That is the whole type. No diagonals; a `Direction` carries no distance.

## 2. `Scene` connections — passive, id-only

Four new methods on `Scene`:

```java
void                  setConnection(Direction direction, UUID neighbourId);   // replaces whatever was there
boolean               removeConnection(Direction direction);                  // false if nothing was there
UUID                  getConnection(Direction direction);                     // null if no neighbour that way
Map<Direction, UUID>  getConnections();                                       // fresh copy, only connected directions present
```

**`Scene` stays deliberately passive about the graph.** It stores raw neighbour **ids** and
nothing else — it never resolves an id to a `Scene`, never loads anything, and each mutator
touches **only this Scene**. There is no validation: a caller may even store a Scene's own id,
and `Scene` won't notice.

**Keeping a link's two sides consistent is the consumer's job.** To join Scene A to Scene B
northward:

```java
a.setConnection(Direction.NORTH, b.getId());
b.setConnection(Direction.NORTH.opposite(), a.getId());   // SOUTH
// then persist both A and B in one transaction
```

The natural home for that pairing + transaction is a service one layer up that owns the `Scene`
repository — this core has neither a repository nor a transaction boundary. `Direction.opposite()`
is the only help this core gives that service.

**Reading the graph:** `getConnection(direction)` hands back a `UUID`; the consumer resolves it
to a `Scene` itself (lazily, from a cache/repository), so loading one Scene never drags its
neighbours in. Anything transitive — a minimap, "rooms within N steps", travel — is built on
top; this core stops at "who is directly adjacent, and which way".

**Lifecycle:** connections are map topology, untouched by `next()`, `startNewRound()`,
`startNewScene()`, `startCombat()`. Set once, they stay until a caller clears them.

**`SceneContext`:** connections are not carried into it — which Scene lies north is not
roll-relevant snapshot state, the same treatment `itemStore` gets.

## 3. `new Scene(UUID id)` — reconstruct with a saved identity

```java
Scene rebuilt = new Scene(savedId);   // rebuilt.getId() == savedId
```

`Scene.id` was a random `UUID` with no way to restore a saved value; now the no-arg
constructor generates one (as before) and `Scene(UUID)` takes an existing one — the same split
`CharacterSheet.of(character, player, id)` gives a sheet. `null` is rejected
(`NullPointerException`).

This makes `Scene#getId()` usable as the key your `setConnection` ids point at: load Scene A,
read `a.getConnection(NORTH)`, and it equals the `getId()` of Scene B once B is reconstructed
with `new Scene(bSavedId)`.

**Every id in the Scene graph is now restorable** end to end:

| Id | How it's restored |
|---|---|
| `Scene#getId()` | `new Scene(savedId)` — **new this release** |
| `InitiativeEntry` sub-group | `addParticipant(sheet, initiativeValue, savedGroupId)` — the 3-arg overload, already there |
| `CharacterSheet#getId()` | `CharacterSheet.of(character, player, savedId)` — already there |
| `Character#getId()` | `Character.builder().id(savedId)` / `.toBuilder().id(savedId)` — already there |

The full rebuild order for a persisted Scene: `new Scene(savedId)` → `setConnection(...)` per
stored edge → add rotation participants (with saved group ids, while the cursor is still `-1`)
→ `restoreTurnCursor(round, index)` → add mid-round joiners → `setCombatScene(true)` if it was
already a Cena de Combate. (See the `Scene` class javadoc.)
