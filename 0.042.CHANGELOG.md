# Changelog — aventyrs-core 0.0.42

**`SantoAbility.GUARDA_VIDAS` is built.** Getting there closed three gaps that were worth closing
on their own: a Tempo de Ativação is now a type rather than a number, a teleportation's *reach* is
now real data, and a client can finally ask what Reações a combatant may take right now.

## ⚠️ Breaking changes

- **`ActiveAbility#getActionPointCost()` and `AventyrTitleAbility#getActionPointCost()` return
  `ActionCost`, not `int`.** Every implementer needs updating; the three `ActiveAbility`
  implementations that returned `0` to mean "Ação Livre" now say `ActionCost.FREE_ACTION` outright.
- **`AventyrTitleAbility#isReactionActivation()` and `#isFreeActionActivation()` are gone.** Both
  folded into the one cost. A constant that overrode either now names `ActionCost.REACTION` /
  `ActionCost.FREE_ACTION` in its constructor arguments instead — which is what lets
  `AbencoadoPelaLuzAbility#GLORIA_RELAMPEJANTE_DE_TESLA` and
  `AbracadoPelaEscuridaoAbility#FUROR_DE_SYLPH` drop the anonymous class bodies they needed purely
  to say "Ação Livre" on an enum with no field for it.
- **`ActionCost.Kind.ACTION_POINTS` is renamed `FIXED`**, beside the new `NONE` and `DYNAMIC`.

## `ActionCost` — one Tempo de Ativação type

`sheet/ActionCost.java` was already the right shape for three of the five cases and was used only
to *record* what an action cost. It now also *declares* what one costs, and both trait interfaces
use it, joining `ChargeService#getActionPointCost` and `WeaponDrawService#DEFAULT_DRAW_COST`, which
already did.

| Kind | `actionPoints` | Means |
|---|---|---|
| `NONE` | 0 | No action at all — a passive |
| `FIXED` | `>= 1` | "Custo de Ativação: NPA" |
| `FREE_ACTION` | 0 | An Ação Livre |
| `REACTION` | 0 | A Reação |
| `DYNAMIC` | `>= 1` | "Variável", from that **minimum** upward |

- New API lifted from `title/PDCost.java`, the house precedent for a fixed-vs-player-chosen cost:
  `dynamic(int)`, `minimum()`, `accepts(int)`, `resolve(int)`, `isDynamic()`.
- **`DYNAMIC` is declaration-only.** It states a price whose amount nobody has chosen yet, so
  `spentActionPoints()` throws on it and `CombatantAction`'s compact constructor refuses one —
  `resolve(spent)` turns it into the `FIXED` payment first. That keeps
  `AssassinoFeat#SAQUE_RELAMPAGO` safe when it reads a recorded action's cost.
- **`NONE` is not `FREE_ACTION`.** An Ação Livre is a player-triggered action that spends no PA; a
  passive is no action. `AventyrTitleAbility#isPassive()` is now exactly `kind() == NONE`, which
  picks out the same constants the old three-part formula did.
- **No `ActionPointCost` type was added.** One cost type, used at both ends, the way `PDCost`
  declares and `InteractionResult#determinationPointsSpent` records on the PD side.

### The cost now decides which counter is checked

`ActiveAbilityServiceImpl#activate` branched: a `FIXED`/`DYNAMIC` cost gates on
`ActionPointsService#getMaxActionPoints` (a `DYNAMIC` one against its minimum), a `REACTION` on
`ReactionsService#getTotalReactions`, an `FREE_ACTION` on `FreeActionsService#getTotalFreeActions`,
and a `NONE` on nothing. New `NOT_ENOUGH_REACTIONS`/`NOT_ENOUGH_FREE_ACTIONS` messages, and a
5-argument constructor taking the two new services (the shorter ones wire the `Impl`s).

⚠️ All three stay **"entitled to any at all"** checks, not live pools: this core still keeps no
spent-this-Turn ledger for PA, Reações or Ações Livres. A holder with one Reação who already used
it this Rodada still passes. Same "reported, not deducted" stance as everywhere else.

## `Teleportation` — a reach, not a move

New `scene/Teleportation.java`: `record Teleportation(int unidadesDeDistancia)` with `of(Range)`,
`asRange()` and `reaches(Range)`, and a new `AventyrTitleAbility#resolveTeleportation()` hook.

**It reports; the caller applies.** This core still does no geometry — nobody has a position and a
`SceneContext`'s distances are a caller-supplied map — so a teleportation answers only "is that
destination within reach", and the client updates the distance map it feeds the next
`Scene#buildContext`. Same division of labour as `Scene#refreshAura`. A `null` distance is *not*
reachable: "cannot tell" refuses.

Deliberately **not** added: a `TeleportationService` (the only check anyone needs is one line, in
the one ability that has it) and hooks on `Feat`/`AttributeAbility`/`Spell`. `TransporteSpell`'s
teleport line is still blocked on geometry, and `PISCAR`'s "1d6+Metade do Foco UD" reach is
computed per-cast, so it wants a `Character`-taking overload this has no business guessing at yet.

## `ReactionOptionsService` — what can I react with?

New `character/services/ReactionOptionsService` + `Impl`, plus `action/ReactionTrigger` (one
constant, `ALLY_TARGETED_BY_ATTACK`, the way `Manoeuvre` has one), `action/ReactionContext`
(`@Builder`, the `TitleAbilityActivationRequest` shape) and `action/ReactionOption`.

`getAvailableReactions(context)` scans the reactor's held Habilidades de Título for a `REACTION`
cost whose `getReactionTrigger()` matches and whose own `isReactionAvailable(context)` holds, and
reports each with its cost, PD price, teleport reach and affordability.

- **A `null` `SceneContext` yields an empty list** — "cannot tell" is nobody, not everybody, the
  rule `MovementReactionService` already follows.
- **An unaffordable Reação is reported, not filtered.** A client greys it out rather than hiding a
  Suprema the player knows they own.
- **Habilidades de Título only.** The only trait type with a Reação today. An `ActiveAbility`
  *could* now declare one and none does; a `Feat`/`AttributeAbility`/`EgoAdvantage` has no reaction
  concept at all.
- Still missing, and the thing to cite: **nothing fires or spends a Reação.** This reports the
  opportunity; `ReactionsService` reports a maximum. Neither counts one as used.

## Guarda-Vidas

`SantoAbility#GUARDA_VIDAS` now names a `GuardaVidasInteraction` and overrides the three new hooks
(`ALLY_TARGETED_BY_ATTACK`, `Teleportation.of(Range.DISTANCIA_CURTA)`, and an availability check
that the threatened ally is really an ally and really within reach).

**The interception works because the attack does not exist yet.** This is a Reação taken *before
the defender rolls*: the client lists it, activates it, and only then builds its
`IncomingAttack`/`DeliveredAttack` naming the Santo as defender. `AttackDelivery`, `AttackReceiver`,
`DeliveredAttack` and `IncomingAttack` are **unchanged** and never learn a Reação occurred. That is
also what makes "o ataque ainda deve superar as suas Defesas" true by construction — the attack is
rolled against the Santo's own sheet from the start, so the `Santo#getDefesasBonus` gap the old
TODO cited never comes up.

The one new reporting field is `InteractionResult#redirectedAttackTarget`, `null` on everything
that is not an interception.

⚠️ Still missing: nothing counts a spent Reação, so a Santo who has already used theirs this Rodada
is still offered this one. `ConditionType#POSSESSAO`'s "ataca o aliado mais próximo" is a separate,
still-open half of the targeting gap — this closes the pre-roll redirect, not mid-resolution
interception in general.
