# Changelog — aventyrs-core 0.0.18

Written for projects that consume this library. Everything below is the delta since the range
`0.017.CHANGELOG.md` covers (through commit `da8b1fb`, "Atack receiver and the Result").

`build.gradle` declares `version '0.0.18'`.

This version has one theme: **a character's condition is asked for, not stored.**
`CharacterStatus` stops being a field that six of eight damage paths forgot to update, and
becomes a derivation that is correct whenever you ask. The same discipline then unblocks the
first continuous cross-character passive — Santo's Bastião dos Necessitados — without adding
any grant, revoke, or event mechanism.

The downstream cost is small: two lines in the JavaFX client, a version pin in the API.

---

## 1. Breaking changes

### 1.1 `Character#getStatus()` and `Character#updateStatus(CharacterStatus)` removed

`Character` no longer stores a status. The field, its Lombok getter, and the builder's
`status(...)` setter are all gone, as is the package-private all-args constructor parameter.

Replace every read with the new derived getter:

```java
// before
CharacterStatus tier = character.getStatus();
// after
CharacterStatus tier = hitPointsService.getStatus(combatantSheet);
```

Nothing in this repository or either downstream consumer ever *set* it —
`@Builder.Default status = CLEAN` had never once been overridden — so there is no
round-trip to preserve. If you populate a `Character` reflectively or from a fixture template,
drop the `status` entry; a stale one now throws (this is how `CharacterFixture` broke during
the migration).

**The `CharacterStatus` enum itself is unchanged** and stays exactly where it is
(`org.aventyrs.core.character.CharacterStatus`). Both downstream consumers import it as a DTO
field type and keep compiling.

### 1.2 `DamageService#refreshStatus(CombatantSheet)` removed

Its whole contract was "recompute *and* store". With nothing to store, the name was a lie and a
pure delegate would have duplicated `HitPointsService#getStatus(CombatantSheet)` on a service
whose job is damage mitigation. Callers that wanted the return value use the new getter; callers
that wanted the side effect no longer need one.

`applyDamage` no longer calls it — see §3.2.

### 1.3 `RealExecution(CriticalResult, HitPointsService)` removed

The two-arg constructor was unused (nothing in `src/main` or `src/test` ever called it). The
service is now inherited from `AbstractEffect`; the one-arg constructor is unchanged.

### 1.4 Non-breaking, stated explicitly

If you **persist** a status tier of your own, keep doing so and change nothing.
aventyrs-api's `CharacterEntry.status` / `CharacterDto.status` and the client's
`CharacterFields.status` are boundary denormalizations — a last-known tier stored beside the
stored damage, so a client can render a token for a sheet it hasn't hydrated. They were never
written from a core `Character`, and nothing in core writes one now. Do not delete them for
symmetry.

## 2. New features

### 2.1 `HitPointsService#getStatus(CombatantSheet)`

```java
CharacterStatus getStatus(CombatantSheet characterSheet);
```

Derives the tier from `getMaxHitPoints(sheet.getCharacter()) - sheet.getDamageTaken()` and hands
it to the pure `getStatus(int, int)`, which is unchanged and still public.

That subtraction is deliberately **unclamped** — not `getCurrentHitPoints`, which floors at zero.
The negative range is what distinguishes `FALLEN` from `COMMA` from `DEAD`, so a clamped
implementation would pin a character at `FALLEN` forever.
`HitPointsServiceTest#statusFromASheetUsesUnclampedHitPointsSoDeathTiersAreReachable` guards it.

It is on `HitPointsService` rather than on `CombatantSheet` — which holds both halves of the
input and would read more naturally — because `org.aventyrs.core.sheet` does not depend on
`org.aventyrs.core.character.services`, and resolving a maximum needs `getMaxHitPoints`'s
Vigor/Life-Multiplier scan. Putting it on the sheet would invert that dependency.

### 2.2 `AbstractEffect#resolveStatus(CombatantSheet)`

`AbstractEffect` now holds a `protected final HitPointsService` (no-arg constructor defaults it;
a `protected AbstractEffect(HitPointsService)` exists for tests) and exposes
`protected CharacterStatus resolveStatus(CombatantSheet)`. Every concrete Effect reports through
it. If you subclass `AbstractEffect` outside this library, both constructors are available and
the no-arg one keeps existing subclasses source-compatible.

### 2.3 `AventyrTitleAbility#resolveAllyAbsoluteDamageReduction`, and Bastião's ally half

```java
default int resolveAllyAbsoluteDamageReduction(SceneContext sceneContext, boolean allyHasLowerPv) {
    return 0;
}
```

The outward half of an ability that continuously buffs someone else.
`SantoAbility.BASTIAO_DOS_NECESSITADOS` now implements both halves of its rules text — the
ally-facing clause ("Aliados adjacentes, apenas aqueles com menos PV que você, recebem RA") was
previously TODO'd for want of a mechanism.

`DamageServiceImpl` reaches it by **scanning**: `sumAllyGrantedAbsoluteDamageReduction` walks
`sceneContext.getAlliesWithin(ADJACENTE)` and asks each neighbour's Título abilities what they
grant outward. This is the opposite direction from every other source in the RA calculation,
which all start from the target's own traits.

Deliberately **not** a `Blessing`/`TemporaryBonus` grant. A granted bonus is a snapshot: it would
need revoking the moment either character moved out of adjacency, died, or left the Scene, and
something would have to notice each of those. Scanned at damage-calculation time, the answer is
correct by construction as characters move — nothing granted, nothing revoked, nothing persisted.
See `BastiaoDosNecessitadosTest#theGrantIsWithheldOnceTheAllyIsNoLongerAdjacent`: no revocation
runs anywhere in it; only the `SceneContext` differs between the two assertions.

## 3. Behavior changes (no signature change)

### 3.1 Every reported `resultStatus` is now true when reported

`InteractionResult#getResultStatus()` is derived at the moment it is built, so the seven
Interactions that previously echoed a stored field now report reality:

| Path | Before | Now |
|---|---|---|
| `Bleeding` / `Withering` per-Rodada loss | tier frozen; a character could bleed to `DEAD` reading `CLEAN` | moves every Rodada |
| `Sangramento`'s own immediate 2 PV | reported the tier from *before* its own damage | reports what it produced |
| `CombatantSheet#heal`, `RestService#applyRest` | never moved the tier at all | moves it, **including upward** |
| Abençoado pela Luz's touch heal | reported the pre-heal tier | reports the post-heal tier |
| `Definhar`, `ManaPurge`, `Primor`, `Sabotage`, Perícia rolls | whatever was last written | the target's tier right now |

Recovering Hit Points moving the reported tier back up is new; nothing in 0.0.17 could do it.

### 3.2 `applyDamage` no longer mutates the `Character`

`DamageService#applyDamage` mitigates and applies, and that is all. It previously also wrote the
`Character`'s status as a side effect.

### 3.3 A character adjacent to a Bastião holder now gets RA

See §2.3. It appears and disappears with adjacency and with the PV comparison, on every
calculation, with nothing granted or revoked.

## 5. Migration checklist

1. Replace `character.getStatus()` with `hitPointsService.getStatus(sheet)`.
2. Replace `damageService.refreshStatus(sheet)` with the same call.
3. Drop any `.status(...)` from a `Character` builder, fixture template, or reflective mapper —
   a stale entry now throws rather than being ignored.
4. If you persist a status tier of your own, **keep it** (§1.4). Nothing in core writes one now,
   and nothing wrote one reliably before.
5. Re-check any assertion shaped
   `assertEquals(x.getCharacter().getStatus(), result.getResultStatus())`. Eleven such
   assertions existed in this repository; every one compared the field against a copy of itself
   and was structurally incapable of failing. They now need a real expected value.
6. `RealExecution`'s two-arg constructor is gone; use the one-arg form.

## 6. Known issues and deliberate gaps

### 6.1 Carried forward from 0.0.17

Two pre-existing test failures, unrelated to this range and unchanged:
`SizeCategoryTest#shiftClampsAtThePlusFourCeiling` and
`CharacterSizeServiceTest#bonusIsClampedAtThePlusFourCeiling`.

### 6.2 `HitPointsService` is asymmetric

`getCurrentHitPoints(Character, CombatantSheet)` takes both; `getStatus(CombatantSheet)` takes
only the sheet, matching `DamageService`'s stated preference. Deliberately not harmonized here —
that is a separate change with its own downstream cost.

### 6.3 The observer question, and what would reopen it

An observer/event mechanism was considered for this work and rejected again. Recorded so it is
not re-litigated:

- **Proximity buffs do not need one.** A pull is not merely sufficient, it is *better*: push
  creates revocation and persistence obligations for a value that is pure derivation. §2.3.
- **Movement-triggered Reações** (`POSICIONAMENTO_ESTRATEGICO`, `AS_NA_MANGA`) are blocked on
  something deeper than events: core has no movement *action*, `Scene` tracks no positions
  (`GridPosition` appears nowhere in `Scene.java`), and `MovementService` returns a UD budget,
  not a displacement. Precondition for reopening: movement exists in core as an operation.
- **Resource-spend triggers** (`AS_NA_MANGA`) — try the cheaper option first: make the spend
  mutator *return* a report of what it triggered, which is core's existing "resolve, don't
  mutate" idiom rather than a new mechanism.
- **`GUARDA_VIDAS` / `PROTETOR_DA_VIDA_E_DA_MORTE`** need attack resolution to become an
  interruptible multi-stage transaction — deeper than an event bus; `combat/` is report-only by
  design.
- Any future observer must answer the **`toBuilder()` identity-swap problem**:
  `AttributeAbilityService` returns a *new* `Character`, so a listener registered on the
  pre-grant instance is silently orphaned.

### 6.4 Ally-facing grants: what is still missing

`resolveAllyAbsoluteDamageReduction` covers Título abilities granting **RA**. Not built:

- **Santo Despertar's ally-facing Defesas half** — needs the same scan on `DefenseService`, and
  first needs `Santo#getDefesasBonus(SceneContext)` promoted from the concrete class to the
  interface so a scan can reach it. This is the second real consumer that would justify
  generalizing the hook beyond Títulos-and-RA.
- **`AttentionCompetencyAbility.INSTINTO_DE_LUTHER`** at 5+ Graduações — same shape on
  `SkillCompetencyAbility`, additionally blocked on Cena-scoped usage tracking.

### 6.5 Nothing drives the Scene loop

Unchanged from 0.0.17, but worth stating since §3.1 depends on it: `Scene#next()` — and
therefore `finishTurn()` / `tickTemporaryEffects()` — has no production caller in either
downstream consumer. The per-Rodada tiers in §3.1 are correct whenever something *does* drive
the loop; today only tests do.
